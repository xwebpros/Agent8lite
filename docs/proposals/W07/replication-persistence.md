# W07 PostgreSQL mock replication persistence proposal

Status: proposed prerequisite; no SQL sink or worker registration is implemented by this document. This follows `replication-boundary.md`, the owned one-page helper in `packages/mls/replication.ts`, and the corrected test ledger in `tests/mls/replication-fixtures.ts`. It addresses MOD-F-005, MOD-F-006, MOD-F-008 and the MOD-C-009 requirement to invalidate derived property surfaces. It does not establish M5 completion.

The schema inventory below was checked against the coordinator's approved migrations 0001–0016. The coordinator owns subsequent allocation, migrations, provider ports, internal schemas and worker registration. This proposal reserves no migration number; 0017 was allocated to M4. No shared schema, contract, role, database, source configuration or credential is changed here.

## Proposed forward migration

Add three MLS-owned ledgers, all with FORCE RLS, tenant-qualified foreign keys, explicit bounds and no runtime DELETE/TRUNCATE authority:

1. `app.mls_replication_page_receipt`: append-only key `(tenant_id, feed_id, resource, receipt_id)`; unique `(tenant_id, checkpoint_id, expected_checkpoint_revision)` and `(tenant_id, checkpoint_id, expected_sql_row_version)`. Store job/run/initiating-user/member IDs, policy version, stream generation, feed revision, rights fingerprint, source-proof digest, expected/next helper revisions and checkpoint digests, expected/next SQL row versions, committed DB time and closed counts. Link to the same tenant/feed checkpoint and run. The helper's SHA-256 receipt identifies the immutable plan; it does not independently authenticate the additional source proof. Reuse with a different proof or binding fails.
2. `app.mls_replication_source_state`: key `(tenant_id, feed_id, source_listing_key)`, nullable native `listing_id`, approved stream generation, latest applied sequence/change identity, current source-content hash, row version and sticky tombstone kind/time. A first-seen deletion creates state with no listing UUID. It must still prevent a subsequent unproved resurrection.
3. `app.mls_replication_source_version`: append-only key `(tenant_id, feed_id, stream_generation, source_change_id)` and unique `(tenant_id, feed_id, stream_generation, source_sequence)`. Store source key, operation kind, canonical source-content hash, disposition (`applied`, `historical` or `tombstoned`), first page receipt, DB observation time and optional native listing/version/outbox reference. Retain every observed identity, including safely ignored historical changes. Known replay uses the existing row and contributes only to the new page's replay count.

Add nullable server-only `replication_policy_version`, `mock_stream_generation` and `mock_order_profile` to `mls_feed`. The initial supported profile is `ordered-synthetic-v1`. These are separate from closed DisplayPolicy/MlsPolicy JSON. Null or unknown values deny the new worker; there is no permissive backfill or implicit policy approval. A reviewed source configuration change increments the feed revision.

Add nullable, immutable `job_id`, `requesting_member_id`, `initiating_actor_id`, `policy_version` and `stream_generation` to `mls_sync_run`, plus mutable `claim_fence` and `retry_not_before`. Require complete bindings for job kind `native-mock-mls-replication-v1` and one run per bound job. Claims use the existing job lease and attempt counter plus a freshly generated fence; a superseded or expired claim cannot pass the final advancement guard. No actor is inferred from a queue body or assigned to a legacy run.

Use `mls_checkpoint.cursor` for the complete validated `MockReplicationCheckpoint`, rather than a second, incomplete cursor representation. Keep SQL `row_version` separate: helper revision starts at zero and SQL versions start at one. Compare both; never substitute one for the other. Mirror only the last completed watermark in `watermark_at`; leave `metadata_hash` for its existing source-metadata purpose. Add nullable `last_replication_receipt_id`, with a deferred tenant/feed/resource receipt FK and a deferred advancement guard that requires the matching receipt's next checkpoint digest/revision and SQL version. Initialization is the sole receipt-free boundary: a bound newly authorized run, helper revision zero and no prior state. An arbitrary checkpoint-only UPDATE must fail.

Add the composite unique keys required to enforce tenant/feed/key relationships, including listing identity versus source state and feed versus run/checkpoint/receipt. Make first-page receipt references deferred so source-version insertion can precede the receipt within the atomic transaction; all dependencies must validate before commit. A tenant-only FK is insufficient if it permits a receipt or source state to point at another feed in the same organization. Existing checkpoints or listings are adopted only through an explicit reviewed reconciliation; their update times, opaque tokens or content hashes do not establish source order.

The first mock configuration is bounded to 20 feeds and 500 listing rows per organization, including unavailable rows, as native reads already require. Proposed additional ceilings are 500 source-state keys, 10,000 source-version identities and 1,000 page receipts per organization. A tenant-scoped transaction lock serializes these budgets across feeds; a per-checkpoint lock serializes each stream. Exceeding a bound rolls back and pauses work. These proposed ceilings require coordinator approval, and are not production retention policy.

## Trusted initiating actor and source ordering

Reuse the existing operator-configured `TrustedContextRegistry` and its closed `{version: 1, contextKey}` wakeup envelope. Its key resolves a trusted organization/user pair; it is not permission evidence. A separate approved MLS dispatcher polls scoped PostgreSQL jobs, with recovery over the same configured contexts even when Redis is unavailable. Do not route MLS events through the reference lead consumer or introduce global tenant discovery/RLS bypass. The initiating command must reject an unconfigured recovery context for this bounded implementation.

An approved command port derives tenant, user and membership from the verified session, checks current organization-scoped `mls.sync` and the current `mls` entitlement, then atomically creates the job/run, command receipt and audit. Initialize a checkpoint only if absent; otherwise use the current matching durable boundary. The public Job body remains frozen. Worker transactions use `withTenantTransaction` with membership/role locking enabled and require the current user/member to match both stored job requester and immutable run initiator. Queue hints and request bodies cannot choose those identities. Own/team grants, inactive membership, unavailable organization, missing capability and unsupported job kinds deny.

The existing `SourceChange` has no stable change ID, sequence or generation. Tied/null `sourceModifiedAt`, timestamp-free deletes, cursor hashes and delivery order cannot fill that gap. The current mock log is process-local; reconstructing the adapter resets its history. Therefore registration also requires a provider-owner-reviewed internal ordered mock read port, without changing the frozen public adapter interface:

- Input binds the trusted context, approved stream generation and unchanged opaque paging input.
- Output contains the closed canonical page and a closed proof: UUID generation, SHA-256 digest of that exact normalized page, and at most 100 `{index, changeId, sequence}` entries, one per operation. Indices match the page; change IDs are bounded nonempty strings (maximum 200 characters); sequences are positive safe integers, unique, stable across replay and ordered by the source manifest for new operations. Propose a coordinator-owned `mock-replication-source-proof-v1.schema.json` before implementing this port.
- Proof comes from a reviewed immutable versioned synthetic change manifest or a separately approved durable mock journal. Restart must reproduce the same identities and generation. It must not wrap an arbitrary process-local array with newly invented sequences, decode a cursor offset, or silently generate a new stream after a reset.
- The trusted read/commit service closure binds proof to the immutable helper plan, job/fence and expected SQL checkpoint version. The current helper receipt does not include this proof; persist and compare its separate digest. No browser, caller or wakeup supplies proof.

For A active → B pending → historical A, A and B retain distinct durable identities even if their timestamps tie. Known A replay does not overwrite B or renew A's freshness, including if a later page fails. An unseen older available upsert is recorded as historical without replacing the listing. An unseen withdrawal/deletion conservatively tombstones the key even if delivered late, without decreasing its highest observed sequence; reconciliation must settle any conflicting later availability. A reused identity with changed content, sequence collision or generation mismatch blocks the entire page. A genuine later return to A needs a new, higher proven source identity; content hashing alone cannot distinguish it from replay. Any missing/ambiguous proof stops for reconciliation with the checkpoint unchanged.

Canonical source-content hashing includes operation kind/source key and sorted canonical object keys, preserving array order and excluding only local `ingestedAt`/`expiresAt`. The proof's page digest and helper's plan receipt instead bind the exact validated page/plan, including those clocks. None of these hashes grants source or actor authority.

Deletes, closed and off-market operations retain stable native IDs and sticky tombstones. A later upsert cannot reactivate them in this first profile, even with higher sequence; that requires a separate reviewed reactivation rule. Unknown-key deletions retain only source state. No placeholder Listing DTO, replacement UUID or CRM inquiry/contact is created.

The proposed internal services are `startNativeMockReplication` (verified command context), `loadNativeMockReplication` (current-authorized durable boundary/receipt), `claimNativeMockReplication` (registered worker context and fenced job), `readOrderedMockPage` (trusted source proof) and `commitNativeMockReplicationPage` (bound claim, immutable plan, proof and expected SQL version). They are server-only proposals, not exported or registered here. The load service may reconcile a completed job without acquiring a new write lease; it still checks its initiating actor and current permission/capability. A claim is mandatory for any new mutation. Changing policy version, generation or checkpoint options requires stopped-stream reconciliation; the normal worker cannot reset revisions or rewrite checkpoint context.

## One atomic page transaction

Read one mock page outside the persistence transaction after current authorization; no provider request occurs while holding SQL write locks. A durable claim may precede that read, but it cannot acknowledge a page. The commit service performs the following in one transaction:

1. Enter trusted tenant/actor context. Acquire the tenant budget lock, lock current organization/membership/role and job/run/checkpoint, then lock feed/connection and affected listing/source keys in deterministic order. Lock the MLS entitlement after source locks, consistent with the native read boundary. The coordinator must check this order against other writers before registration.
2. Read `clock_timestamp()` after waits. Recheck current `mls.sync`, capability expiry, job/run initiator, cancellation, lease/fence, exact tenant/feed/resource/policy/generation, and the approved synthetic source. Require ready mock feed/transport and the existing read boundary's connection provenance: provider `trestle`, mode/state `mock`, null secret, `safe_config.synthetic=true`, `liveFeedRights=unapproved` and a valid nonfuture policy approval time. Require approved replication rights and finite positive retention/freshness limits. Derive `getMockReplicationFeedBinding` from locked current metadata and compare both revision and rights fingerprint. A still-approved but changed policy is a conflict, not permission to rebase an old plan.
3. Compare the full stored expected checkpoint and its SQL row version. Validate the immutable plan and ordered proof again. A matching prior receipt is read only after current authorization; it may acknowledge only if the authoritative checkpoint still equals its exact next boundary. If progress has moved further, return reload-required. A stale plan never replaces a newer checkpoint or receives a fabricated receipt.
4. Validate every change's representability and approved storage fields before applying it. Preserve the listing UUID at `(tenant, feed, source key)`; classify all identities against the durable ledger in source order. Store closed address/attribution JSON and supported canonical columns only. Canonical bedrooms may not be fractional; price/bathroom/area precision must fit SQL. Zero or `sqm` area requires a separately reviewed mapping; no silent rounding, truncation or invented unit/currency/source ID. The initial approved mock profile must explicitly establish USD pricing because CanonicalListing carries no currency; a SQL default is insufficient evidence. Unknown display rights/status remain unavailable.
5. Apply listing changes, identity state, source-version rows and tombstones. A known identity replay preserves its original ingestion and expiry. Effective freshness cannot exceed the original proven source observation, canonical expiry or current approved data-age/retention limits. Reading historical data or using DB update time cannot refresh it. Only a genuinely new source observation under the approved profile may establish new freshness. Never persist raw provider payloads, media or fields whose replication/storage permission is unresolved.
6. Coalesce changed known listings to their final native version for the page and insert closed invalidation outbox records plus safe audit. Write the page receipt, checkpoint CAS, run counts/progress and job state atomically. Update feed `last_complete_at` only on the final completed page, using committed DB time; completed source watermark remains a separate value. Recheck time-sensitive authority/lease using the current DB clock before final advancement. Checkpoint update requires the receipt dependency; any failed change, constraint, ledger/event/audit insertion or CAS rolls everything back.
7. Commit before returning the helper's matching receipt and exact next checkpoint. No independent checkpoint-write callback exists. Job success means the source cycle committed; it does not claim that derived surfaces have processed invalidations.

Tenant is part of every persisted key and lock scope; stream keys and relationships additionally bind feed/resource where applicable. Two feeds using the same synthetic source key remain independent. Native `row_version` and event versions must remain representable by the internal/event validators; overflow fails explicitly.

## Narrow grants and integrity boundaries

The forward migration must add restrictive command-specific RLS on top of tenant isolation, with actual-role probes for policy composition and recursion. Current actor permission predicates query only membership/role/organization/entitlement; job/run/feed predicates must form an acyclic dependency graph. Do not query a protected table recursively through its own policy. Do not add an unscoped SECURITY DEFINER discovery function or inherit control/issuer privileges.

| Identity | Proposed authority |
| --- | --- |
| Runtime | Approved job/run/checkpoint bootstrap and command receipt only under current `mls.sync`, capability and registered initiating context. Existing native listing reads remain scoped. No listing/source-ledger/outbox-invalidation ingestion writes or source policy/configuration changes. |
| Worker | Scoped job/run/checkpoint/source-state/listing reads and narrowly enumerated persistence columns; append-only page/source-version INSERT; existing audit INSERT; new outbox INSERT restricted to the approved listing invalidation family and matching initiating actor. Job updates cover only own bound MLS claim/progress/retry fields. Feed UPDATE covers `last_complete_at` and its version metadata only. |
| Worker lock privileges | Minimal SELECT and metadata UPDATE privilege needed for current organization/member/role/entitlement/feed/connection SHARE locks, with business mutation rejected. A lock grant must not become rights, membership, entitlement or configuration mutation authority. |
| Migration/configuration owner | Reviewed schema and synthetic source-profile initialization only. Never used by the runtime/worker transaction pool. |

The worker remains non-owner, NOSUPERUSER and NOBYPASSRLS. Immutable run bindings, receipt/version records and audit reject UPDATE/DELETE; INSERT shape constraints and the checkpoint advancement guard are required. Transaction atomicity additionally depends on the single reviewed commit service: grants alone do not prove correct processing of a provider page. No MLS code writes CMS revisions, cache tables, campaigns, alert deliveries or CRM tables directly.

## Closed invalidation and recovery contracts

Propose `packages/contracts/internal/native-mock-listing-invalidation-v1.schema.json`, owned and approved by the coordinator before a consumer. Refine the existing event envelope with producer `native-mock-mls`, aggregate type `listing`, aggregate UUID equal to payload `resourceId`, final committed native `resourceVersion`, exactly one related UUID (the feed), and safe code `synthetic_listing_changed` or `synthetic_listing_withdrawn`. Use `listing.withdrawn` whenever the final mutation makes a known listing unavailable, otherwise `listing.changed`. Validate envelope and relational bindings on both insertion and consumption.

Event ID equals the outbox row ID; tenant and initiating actor are derived from the transaction; event times use the DB clock. At most 100 known listing events are emitted per page, with source-version rows pointing to the coalesced event where applicable. No source key, canonical content, address, contact, token, cursor or complete rights document is in queue, audit or event payloads. Retransmission uses the same outbox ID and per-consumer receipt.

A first-seen deletion has no native listing or registered derived reference to invalidate; persist its tombstone without fabricating an event resource. Supporting untracked legacy or whole-feed caches would require a separate approved feed invalidation port/event. The present proposal does not authorize those caches. The reference lead consumer must defer this event family without acknowledging it.

Future MOD-C/map/image/cache/alert consumers purge or mark references unavailable through their owning ports and reload current scoped listing/feed rights, state and expiry before reuse. An older event cannot restore data after a newer version. Display access fails closed immediately on expiry/revocation; asynchronous cleanup is not display authorization. Expiry sweeps, whole-feed rights invalidation and cleanup after the initiating actor loses access need separate approved ownership/identity contracts. No automatic publication, alert sending, match creation or delivery is implied.

After a lost acknowledgement, reload the checkpoint and receipt under current authorization from PostgreSQL before any further read. If the page committed, use its durable boundary/ledger; if progress advanced further, use the newer authoritative state. If it rolled back, retry only from the unchanged boundary with a valid claim and proof. Never retry an unknown commit by inventing a new revision. Process restart uses the same configured trusted registry, persisted jobs/claims and source generation; duplicate/lost Redis hints do not create jobs or remove committed work.

429 uses the helper's bounded 1–3600 second delay persisted as DB-clock `retry_not_before`; no automatic tight loop. Credential/cursor expiry and unknown faults retain the completed watermark/checkpoint and a fixed safe failure. Restart from the last completed watermark requires reviewed reconciliation and the same identity/tombstone ledger. The coordinator must approve retention for hashes/source keys as well as listing data: ledgers are not assumed exempt from licensing. Stop at identity-retention or budget limits; do not prune replay evidence and continue, renew data expiry, or rotate generations automatically. Destructive retention cleanup requires a separately reviewed stopped-stream reconciliation.

## Required acceptance before worker registration

These are proposed checks, not executed results. Use an isolated disposable PostgreSQL/PostGIS database with the approved forward migrations plus the allocated candidate, and actual runtime/worker non-owner roles. No shared estate, role mutation outside that disposable harness, browser, provider credentials or live Property requests are needed.

| Gate | Required evidence |
| --- | --- |
| Migration and roles | Fresh/forward application without reset; FORCE RLS and composite FKs; unchanged control/issuer separation; legacy null bindings deny; frozen public contracts still validate. |
| Context and scope | Missing context, pooled connection reuse, cross-organization feed/run/receipt, same-key cross-feed collision, forged hint/actor, unconfigured recovery context and own/team-only grant fail without mutation. |
| Write boundaries | Runtime source writes, worker source-policy/configuration writes, immutable binding/ledger/audit edits, and checkpoint-only advancement fail; lock privileges permit locks without business edits. |
| Current authority | Revoke member/role/grant or expire capability while a source lock is blocked; change policy/connection/generation after read; expire lease or supersede fence. After the wait, DB-clock/current-row checks deny with every page tuple unchanged. |
| Atomicity and CAS | Fail at each write boundary, including the Nth change, receipt, outbox and final checkpoint. No partial listing/ledger/tombstone/event survives. Concurrent claims/plans yield one accepted boundary, no duplicate native ID. |
| Durable ordering | Equal/null timestamps; A → B → historical A with following-page failure; canonical key-order variations; unseen older identity; new proven return to A; reused identity with different content; sequence collision and absent proof. Verify stable B and unchanged clocks on replay using separate connections/restarts. |
| Tombstones and bounds | Known/unknown deletion, closed/off-market withdrawal and attempted resurrection retain identity/unavailability. Precision, byte/page/cursor, 500-row/source-state and ledger/receipt bounds fail explicitly without truncation. |
| Crash and wakeup recovery | Before-commit crash rolls back; after-commit lost acknowledgement reloads the exact durable checkpoint/receipt without reapplying source effects. Adapter/worker restart preserves proof generation. Missing/duplicate hints recover authorized DB work; forged hints fail. |
| Failure/freshness | 429 schedules bounded DB retry; cursor/credential faults preserve checkpoint. Stale source observations and content replay do not refresh ingestion/expiry; native projections deny expired/withdrawn data. |
| Invalidation | Envelope, tenant/aggregate/version/feed/actor links and payload privacy validate; source replay creates no duplicate event. Wrong consumer defers. Future purge acceptance separately proves out-of-order/idempotent handling without publication or delivery. |
