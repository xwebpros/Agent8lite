# Proposed local recovery read — awaiting coordinator review

The frozen Revision schema cannot represent future block kinds. Its existing get/list operations must retain `409 revision_recovery_required`; the editor must not widen that envelope, drop unknown blocks or infer the latest revision from UUID pagination.

Proposed additive synthetic-development read: `GET /dev/orgs/{orgId}/cms/documents/{documentId}/revisions/{revisionId}/recovery`. It uses the same loopback/session/selected-organization boundary, current organization `content.read`, websites capability, administration profile reference and source locks as the reviewed CMS reader. The revision must belong to the path document. Authorization is rechecked after locks. Missing, foreign and ineligible resources return the existing safe Problem. No mutation, automatic repair, save or publication follows this read.

The successful JSON object is closed: exactly `id` (UUID), `documentId` (UUID), `data` (bounded original JSON), `issues` (array of closed `{path: string, code: string}` objects), `canSave: false`, `canPublish: false`. The raw `data` is the existing service recovery payload `{schemaVersion, blocks, seo}`, preserved rather than projected onto the frozen block enum. Response headers are `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and the ordinary trace header; there is no new document-version ETag on this immutable read. Registered revisions use the frozen normal reader. Recovery remains read-only even if all current validators accept the payload.

The reader retains the registry's 256 KiB / 32-depth / 20,000-node limits and safe issue paths/codes. Transport limits must allow JSON escaping/envelope overhead while remaining bounded. If original content cannot be represented within these limits, return a safe error; never truncate or normalize it into an editable draft. No private JSON goes into logs, audit, localStorage, IndexedDB or service-worker caches. Render recovery as escaped text, never tenant HTML or a link preview. The browser may accept an already-authorized recovery payload through an injected adapter; it will not implement this HTTP fetch or consume a new client contract before review.

Future-kind history discovery is a separate unresolved boundary: frozen PageRevision cannot describe such a row, and this proposal does not replace its items with another shape. Root can supply an explicit known revision ID after an authorized workflow; a recovery index/metadata envelope needs its own review. Router/BFF registration and shared contracts stay coordinator-owned. Puck, public preview/publish/rollback and complete M3 acceptance remain gated.
