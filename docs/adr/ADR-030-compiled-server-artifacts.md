# ADR-030 — Pinned compiled API and worker artifacts

Accepted bounded W01/W11 build preparation on2026-10-10 before consumer changes. The selected XWeb Pros target requires repeatable web/API/worker artifacts. This decision adds a local build/start seam, not host provisioning, production identity, worker discovery, an OCI image or release authorization.

Compile only the API and worker entrypoints and their transitive TypeScript/JSON dependencies using a dedicated configuration derived from the reviewed root CommonJS/Node compiler settings. Use Node24.19.0 and TypeScript5.9.3. Nest12 dependencies are ESM; their synchronous CommonJS loading must be verified on the pinned Node runtime rather than assumed from TypeScript success. Do not compile tests, seed/migration tools, web source or unrelated fixture payloads into this artifact. TypeScript's actual emitted graph and copied JSON resources are the authority.

Build into a fresh owned workspace dist directory, then install the successful result at dist/runtime. The builder checks resolved workspace/target paths and a fixed ownership marker before any recursive cleanup/replacement. Refuse symlinks or unowned existing output. Failed compilation preserves the previous artifact. Output contains an explicit CommonJS package marker and a sorted file/hash/size manifest without timestamps, credentials, environment values or private source payloads. Identical source/runtime builds must have identical manifests. The build directory is not a live deployment release path.

Add compiled API startup using its CommonJS entry identity while preserving the existing source CLI path. Importing the emitted API module must not start a listener. Keep the loopback defaults, synthetic identity checks, current permission/RLS roles, private storage mode and all no-delivery/provider gates. Startup reports the actual identity configuration state; compilation cannot establish production authentication.

Root commands build API/worker plus the Next production build, with separate start commands for each process. Runtime dependencies remain exactly pinned in the existing lockfile. Starting an artifact needs explicitly configured application environments and private role URLs; no build/start command loads ignored secrets, runs migrations/seeds or deploys automatically. Future deployment copies the exact committed release and production dependencies into an immutable release directory and separately supervises web/API/worker.

Verify compilation/resource hashes, repeated manifest equality, import safety and compiled loopback API health plus production synthetic-session denial. Worker verification must not dispatch interactive work: use an explicit empty trusted-context configuration to prove fail-closed startup, then separately use the existing disposable recovery harness for domain behavior. No real outbound calls, server credentials or host connection are needed. Actual Linux/host execution, production identity/private adapters, supervision, backups/recovery and M8 remain open gates.
