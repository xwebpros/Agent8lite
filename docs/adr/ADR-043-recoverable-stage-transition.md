# ADR-043 — Recoverable Lead stage transition

Accepted by the coordinating owner on 2026-10-11 after ADR-041/042 verification. This bounded M2 slice advances MOD-D-007, MOD-D-AC-3, MOD-K-006/007 and the capture → assignment → follow-up exit path. It covers only `POST /v1/orgs/{orgId}/leads/{leadId}/stage-transitions`; Lead PATCH, Task commands, archive/merge and browser/device acceptance remain separate.

Integration clarification (2026-10-13): activity scoring introduced by forward0032 can change the command's derived score without changing its optimistic revision. Fresh receipts capture the exact locked state after synchronous command effects. Client acknowledgement therefore validates the generated Lead schema and a coherent score/scoreVersion pair, rather than requiring the old score to survive a stage change. Null/omitted score requires null/omitted scoreVersion; a scored receipt requires a nonblank version. All command identity, Contact/source linkage, requested stage, expected next revision, strong ETag, owner, intent and timeline checks remain mandatory. Historical receipts remain unchanged and acknowledge only their original command; they never populate the current view.

The frozen operation already requires an idempotency key and returns `201 Lead`, while MOD-D-007 and the existing implementation require optimistic revision. Its parameter list accidentally omitted `If-Match`, unlike the sibling Contact, Lead and Task mutations. Add the exact reviewed `If-Match` header through `packages/contracts/amendments/ADR-043-stage-transition-if-match.json`, apply only that parameter to the implementation OpenAPI and regenerate its client types. The original blueprint remains unchanged. Preserve `StageTransition`, `Lead`, `lead.stage_changed`, `crm.leads.write`, the one-day server receipt duration and existing strong numeric ETag behavior. Do not add a lead-read or pipeline-read prerequisite to the command.

Before any wait, detach and validate the route Lead UUID, closed StageTransition body, printable idempotency key, exact supplied If-Match spelling and verified authority snapshot. Bind the request hash to the detached body and exact header spelling. Serialize by tenant, actor, route and key; inspect an existing receipt regardless of expiry. A changed hash conflicts. A matching expired receipt returns `receipt_expired` without execution, renewal or replacement. Fresh execution and replay require the actual runtime role, matching transaction tenant/actor, active membership/role/organization, exact complete current grants and current CRM capability.

Fresh execution locks the current unarchived Lead and its unarchived Contact, then the current and requested immutable pipeline-stage identities in stable order. Own/team/organization Lead-write scope is evaluated from the current owner. Team scope locks the actor/owner office relationships and rechecks them after waits. Recheck all authority, source, archive, stage and capability evidence using database time immediately before mutation and again before return. Reject unchanged stages and exhausted revisions. Insert one stage history row, update the Lead once, and append one schema-valid privacy-safe `lead.stage_changed` event, one safe activity reference and one audit record in the caller transaction. The event uses database time and carries only reviewed reference IDs/version; the reason and Lead fields never enter outbox or audit payloads.

Replay validates the stored historical Lead strictly against the command identity, expected next version, requested stage and immutable Contact/source linkage recorded by that receipt. It then authorizes the current Lead, Contact, owner/team sources, referenced stages and capability without applying historical values to the current view. A legacy matching receipt with a null stored response ETag is accepted only after validation; otherwise a strong ETag equal to the historical version is required. Replays produce no new stage history, activity, audit or outbox rows.

The tab controller captures the exact Lead identity/reference fields, target stage, optional reason, expected revision, UUID key and verified user/organization/member/CSRF/access-revision/full-grants binding before sending. An ambiguous outcome retains that immutable command and blocks competing commands, route changes, organization switch, sign-out, close and service-worker activation. Explicit reconciliation resends the exact body, key and If-Match for at most 23 hours under both wall and monotonic clocks. A strict matching receipt acknowledges the historical transition; a separate authorized current read refreshes the pipeline. Offline or hidden recovery withholds Lead details. Context/access loss invalidates private state and late callbacks.

ADR-042 local forgetting extends to an expired or clock-invalid unknown stage command with the same exact action and wording: **Clear this tab’s recovery data** sends no request, removes all private command/draft/reference values, invalidates callbacks, releases lifecycle guards, retains a generic warning and blocks another stage command through the same controller binding. A context replacement or document reload may permit a human attempt and cannot prevent a possible duplicate.

Backend owns a dedicated command/receipt boundary and stage service path under `apps/api/**`; frontend owns protocol/panel/workspace integration under `apps/web/**`; tester owns PostgreSQL/RLS, protocol/controller/static acceptance under `tests/**`. Root owns this ADR, the additive parameter amendment, generated contract and integration review. No migration, dependency, new operation, new event type or provider behavior.

Acceptance covers same-key concurrency, distinct revision races, changed/expired receipts, legacy ETag compatibility, historical replay after a later transition, rollback of every effect, write-only own/team/organization scope, foreign/archived sources, membership/grant/capability loss, actual Lead/Contact/stage/office/advisory waits, pool reuse, validated database-clock event privacy and unchanged Lead/Task behavior. Client acceptance covers exact immutable resend, acknowledgement versus current refresh, initial rejection versus unknown outcome, expiry/clocks/forgetting, stale responses, context cuts, navigation/update protection and generic private-safe rendering. Browser/axe/keyboard and physical installed-mode behavior remain open.
