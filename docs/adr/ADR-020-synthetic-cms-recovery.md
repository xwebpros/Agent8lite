# ADR-020 — Authorized synthetic CMS recovery read

Accepted bounded MOD-C-003/004 prerequisite on 2026-10-10, before consumers. The closed internal `native-cms-recovery-v1.schema.json` implements the reviewed W05 recovery proposal. Frozen Revision/PageRevision bodies remain unchanged and still return `409 revision_recovery_required` for unsupported stored content.

The additive local read is `GET /dev/orgs/{orgId}/cms/documents/{documentId}/revisions/{revisionId}/recovery`. Explicit synthetic mode, actual loopback, the selected member organization, current organization-scoped content.read, websites capability, administration profile reference and existing source locks are required. The revision must belong to the exact path document. Recheck permission, capability and source validity after locks with the database clock. Missing, foreign and ineligible resources return safe Problems without original JSON.

The response contains only id, documentId, bounded original data, safe issue paths/codes, canSave:false and canPublish:false. Original schemaVersion/blocks/seo JSON is preserved, including unknown kinds and future versions; recovery never normalizes, repairs, drops content, saves or publishes. The existing 256 KiB original-data, 32-depth and 20,000-node bounds apply. The envelope additionally permits at most 2,000 issues with 1,024-character paths/100-character codes and at most 1 MiB serialized UTF-8 transport. Excessive content or diagnostics fail safely rather than truncate. Even currently supported data remains read-only through this route.

Private/no-store, nosniff and trace headers apply. This immutable recovery response supplies no document ETag; the normal document read remains the authority for an explicit later save's revision precondition. Browser consumers validate the shared internal schema and byte/tree limits, render original data only as escaped text, keep it only in memory and clear it on context loss/offline/expiry. No private data enters logs, audit, service-worker caches, localStorage or IndexedDB.

The first reader can receive an explicit known revision ID. Future-kind history discovery needs a separate approved metadata envelope; frozen PageRevision cannot be widened, omit unknown rows, or claim UUID order identifies the latest revision. Publication, rollback, Puck, media/domain/forms and public responsive acceptance remain separate M3 requirements.

The reviewed W05 history metadata proposal is now approved before its consumers. `GET /dev/orgs/{orgId}/cms/documents/{documentId}/revision-history` returns the closed internal `native-cms-revision-history-v1.schema.json`: at most100 items containing only id, exact documentId, schemaVersion and createdAt, plus hasMore/nextCursor. It includes supported and unsupported native rows without reading their block_data/seo. The same synthetic/member/organization/content.read/websites/profile/source guards and database-clock rechecks apply. Pagination accepts only limit/cursor (default50, limit1–100), rejects repeated/unknown query keys and binds signed expiring cursors to organization/member/document/resource. ID ordering is a stable index, not a snapshot, chronological order or latest-revision inference. Response UTF-8 size is at most64 KiB, with private/no-store/nosniff/trace headers and no ETag or write side effect. Browser consumers verify item/path document binding and schema/size limits; metadata and original recovery clear on offline/context/access loss. Supported editing requires an explicit normal frozen Revision read and strict validation; index metadata alone never proves editability. Frozen PageRevision remains unchanged and may fail safely on unsupported rows. Actual-role mixed-row pagination, cursor/source/expiry/privacy/no-write and registered API acceptance are required before marking this slice verified.

Acceptance covers original unknown JSON preservation, wrong-document/tenant denial, current profile/capability/member revocation and lock-wait expiry, closed output, byte/tree/issue bounds, registered-revision frozen behavior, escaped read-only browser projection and private response headers. API/static checks do not establish browser or physical-device acceptance.
