# ADR-044 — Recoverable Task creation and Lead follow-up

Integration review, 2026-10-13: the existing0032 activity scorer synchronously updates the linked Lead's derived score. Acquire that already authorized linked Lead with `FOR UPDATE` before assignee/office locks to serialize independent Task commands and prevent competing SHARE-to-UPDATE upgrades. This preserves the Task-write-only policy and existing sorted source lock order. Distinct explicit keys must still create distinct Tasks with two201 receipts; same-key retries retain their original receipt. Real-role integration verifies both cases.

Accepted by the coordinating owner on 2026-10-11 after ADR-043 verification. This bounded M2 slice advances MOD-D-007, MOD-B-AC-3, MOD-K-006/007 and the capture → assignment → follow-up exit path. It covers only `POST /v1/orgs/{orgId}/tasks`; Task PATCH/completion, Lead assignment, reminders and browser/device acceptance remain separate.

The frozen operation already requires an idempotency key and returns `201 Task`. Preserve `TaskWrite`, `Task`, `crm.tasks.write`, the one-day server receipt duration and version-1 strong ETag. Task creation has no `If-Match`. Preserve the legacy request hash over the detached body and `expectedVersion: null` so existing unexpired receipts remain replayable. Do not add Task-read, Lead-read or Lead-write prerequisites to a write-only creation command. Do not emit `task.due` at creation; that published event belongs to the due scheduler. A Task linked to a Lead appends one internal privacy-safe `task.created` activity reference, while a standalone Task has no Lead timeline row.

Before any wait, detach and validate the queryless route, closed TaskWrite body and printable idempotency key. Normalize title, due instant, IANA timezone, optional description, priority and state only through the reviewed domain rules; preserve exact original request bytes for client retry and exact canonical legacy hash semantics on the server. Serialize by tenant, actor, route and key, then inspect a matching receipt regardless of expiry. A changed hash conflicts. A matching expired receipt returns `receipt_expired` without execution, renewal or replacement.

Fresh execution and replay require the actual runtime role, matching transaction tenant/actor, active membership/role/organization, exact complete current grants and current CRM capability. Lock and recheck the active assignee and all office relationships needed by own/team/organization Task-write scope. For a linked Task, lock and recheck the unarchived Lead, its unarchived Contact, current owner/team office sources and the exact Lead linkage through the existing Task source policy. Use database time at the final authorization boundary. Reject archived, foreign, inaccessible or substituted sources and exhausted revisions without Task, activity, audit or receipt effects.

Fresh execution inserts one Task, optionally appends one Lead activity row with only Task/Lead IDs and Task version, appends one audit reference and inserts the idempotency receipt in the caller transaction. Replay strictly validates the historical Task against the command identity and every requested field after documented normalization, then authorizes the current Task, current assignee and current optional Lead sources without applying historical values to the current view. A legacy matching receipt with a null stored response ETag is accepted only after validation; otherwise a strong version-1 ETag is required. Replay creates no Task, activity or audit duplicate.

The Add task controller captures the exact validated TaskWrite body, UUID key and verified user/organization/member/CSRF/access-revision/full-grants binding before sending. Due input is converted once to the captured UTC instant and named IANA timezone. An ambiguous outcome retains that immutable command and blocks competing commands, route changes, organization switch, sign-out, close and service-worker activation. Explicit reconciliation resends the exact body and key for at most 23 hours under both wall and monotonic clocks. A strict matching `201 Task`/`ETag: "1"` acknowledges the historical creation; a separate authorized current refresh updates the agenda. Offline or hidden recovery withholds title, description, Lead and timing details. Context/access loss invalidates private state and late callbacks.

ADR-042 local forgetting extends to an expired or clock-invalid unknown Task creation with the exact action **Clear this tab’s recovery data**. It sends no request, removes all private command and draft values, invalidates callbacks, releases lifecycle guards, retains a generic warning and blocks another Task creation through the same controller binding. A context replacement or document reload may permit a human attempt and cannot prevent a possible duplicate.

Backend owns a dedicated Task-create command/receipt boundary and service path under `apps/api/**`; frontend owns protocol/panel/workspace integration under `apps/web/**`; tester owns PostgreSQL/RLS, protocol/controller/static acceptance under `tests/**`. Root owns this ADR and integration review. No migration, dependency, public-contract amendment, new outbox event type or provider behavior is approved.

Acceptance covers same-key concurrency, deliberate new-key duplicates, changed/expired/legacy receipts, historical replay after later Task update, rollback of Task/activity/audit/receipt, standalone versus linked activity, write-only own/team/organization scope, foreign/archived Lead and Contact sources, assignee/member/grant/capability changes, actual advisory/assignee/Lead/Contact/office waits, pool reuse and database-clock evidence. Client acceptance covers exact immutable resend, due-time capture, acknowledgement versus current refresh, initial rejection versus unknown outcome, expiry/clocks/forgetting, stale responses, context cuts, navigation/update protection and generic private-safe rendering. Retain current Task completion and stage-transition behavior. Browser/axe/keyboard and physical installed-mode behavior remain open.
