# ADR-036 — Timezone-aware loaded task agenda

Accepted by the coordinating owner on 2026-10-10 after the stored appointment slice. This bounded M2 frontend slice advances MOD-B-001/003 using the existing generated Task and PageTask contracts, current scoped workspace task reads, the existing task drawer route and existing completion command. No API, schema, dependency, permission or provider change is proposed. It is not a complete daily agenda or a new dashboard aggregation.

Replace only the dashboard's five-record next-steps panel with a reusable loaded-task agenda. Reuse the shell's current tasks, scope, refresh/cursor status, permissions, online/loading/organization-switch state and completion callback. Label every count/group as loaded and disclose partial pagination; do not claim complete inventory, daily totals or synchronization. Completed/cancelled tasks are excluded from open-task timing groups. Keep unrequested/loading/unavailable/offline and verified empty distinct. Hide private rows and disable actions when offline, inactive or changing organization; show stale rows only with a clear refreshing label when their current context remains valid. No private persistence or new request path.

Capture one current UTC instant for each classification. A valid open task is overdue only when its due instant is strictly before that instant. Remaining tasks on the same Gregorian calendar date in the explicitly named user IANA timezone are due today; later local dates are upcoming. Compare dates derived from Intl with an explicit timezone/calendar/numbering system, not workstation-local Date getters, string slicing of UTC dates or fixed 24-hour day arithmetic. Clock updates must reclassify while the mounted dashboard is visible. Missing/invalid current or source timezone/instant is explicitly unavailable with safe UTC reference where valid; never silently use a workstation timezone. Show offset-aware user time, organization time when different and stored source time when different, so DST repeated hours remain distinguishable. Bound rendered rows per group with a loaded/visible disclosure and guarded view-tasks action.

Task title/drawer and completion actions are native buttons. Route to the existing /tasks?task=UUID through a shell callback that synchronously checks current access/online/context, busy/organization-switch state and dirty/unconfirmed-command guards. Completion uses the existing frozen PATCH authorization, revision, idempotency and error/reconciliation behavior; this component must not issue its own command, mint an independent retry key or permit actions while source timing metadata is invalid. No direct Link bypass. Layout preferences cannot widen query scope.

Ownership: frontend owns new apps/web/components/task-agenda.tsx, task-agenda.module.css and task-agenda-time.ts plus the bounded dashboard mount/guard in workspace.tsx. Tester owns tests/unit/task-agenda-time.test.ts and task-agenda.test.tsx. Backend independently reviews the existing task read/completion authorization and current-owner linkage without writing shared files; concrete defects are reported to the coordinator before a separate correction is allocated. Root owns this ADR, status, integration and any shared change. This decision is committed before implementation.

The independent review identified an existing linked-source gap in task reads and commands. The coordinator additionally allocates backend ownership of apps/api/src/crm-service.ts and tester ownership of tests/integration/task-source-access.test.ts for this correction. Linked task reads require current scoped crm.leads.read on the linked lead plus an unarchived lead/contact. Standalone tasks retain their existing task permission. Writes preserve the existing lead-write dependency for linked task creation/change and apply it to the effective current link even when a PATCH omits or clears leadId; a hidden source cannot be bypassed by unlinking. Check proposed links too. Commands and historical replay reauthorize both the current task and any linked source in the original response/request; a newly accessible current link cannot authorize a cached response exposing a revoked historical link. Lock linked lead/contact parents for commands and recheck source/CRM capability after waits. Source-inaccessible task rows/details are hidden consistently. No public shape, role grant, database schema or task delivery authority changes.

The independent review also found a concrete task-completion recovery gap: a failed fingerprint retained its key, but refresh/navigation could replace its original body/version or lose it. The coordinator allocates frontend ownership of an additional task-completion.ts pure helper plus the bounded completeTask/pending guard integration in workspace.tsx, and tester ownership of tests/unit/task-completion.test.ts. Before the first await, retain a detached context-bound original TaskWrite, task UUID, If-Match version and explicit idempotency key. An ambiguous network/JSON/5xx outcome preserves this exact snapshot and protects navigation, organization switch, sign-out and PWA reload; block unrelated task commands. Expose explicit reconciliation through the original snapshot/key/version. A matching validated done receipt acknowledges the command, then an authoritative refresh supplies current state; never insert the historical receipt over a newer task. A definitive 4xx rejection may release the pending command; access/context loss clears its private data and invalidates late completion. Shared guards must include task pending state synchronously, including internal anchor navigation. Do not claim full generic CRM mutation recovery from this task-specific correction. No new server command or persistence is added.

Acceptance: pure instant/date partition tests cover Los Angeles spring/fall, both repeated-hour instants, local-day boundaries, leap dates, non-hour zones, invalid metadata and completed/cancelled exclusion. Existing static React harness checks every state, loaded/partial/visible disclosures, offsets and disabled guarded actions; it does not establish browser or keyboard acceptance. Root reviews callback/current-context integration and runs relevant retained task/CRM tests, combined types/contracts/format/full application build and compiled launcher probes. Browser/axe/keyboard/physical-device and broader M1/M2/M4/M8 gates remain open.
