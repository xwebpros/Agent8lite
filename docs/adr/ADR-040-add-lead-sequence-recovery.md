# ADR-040 — Recoverable Add lead sequence

Accepted by the coordinating owner on 2026-10-11 after verified contact-edit checkpoint `bb67d20`. This bounded M2 slice advances MOD-D-001 and the MOD-K interrupted-command criterion using the frozen createContact and createLead POST operations, generated ContactWrite/Contact/LeadCreate/Lead/Problem schemas and existing `lead.captured` event. Commit this decision before dependent implementation. It adds no public route, contract, event, migration, dependency or provider.

The existing Add lead dialog performs two independent durable commands: Contact POST, followed only after its acknowledgement by Lead POST. The API does not define a compound capture command, so do not claim cross-request atomicity. A contact may be durably created even when no lead is created. No approved `contact.created` event exists; do not invent one. The existing lead row, `lead.captured` activity and `lead.captured` outbox event remain one transaction with the lead receipt and audit. Complete contact-event/INV-03 acceptance remains open pending a reviewed additive event.

Before the first await, capture a bounded detached generated ContactWrite, a bounded lead template containing source, current owner member, intent and timeline, two distinct UUID idempotency keys, and the current verified context. Bind user, organization, member, CSRF, access revision and the complete permission set. Inputs and keys cannot be rebuilt from later form values. The contact command is sent first. Only a schema-valid Contact receipt with status 201, strong `"1"` ETag, version 1 and the same normalized submitted name/email/phone/birthday values may acknowledge it. After acknowledgement, materialize the exact generated LeadCreate using that returned contact UUID and the already captured lead template/key. Only a schema-valid Lead receipt with status 201, strong `"1"` ETag, version 1 and the exact contact/source/owner/intent/timeline may acknowledge the lead. The server-selected stage must be a valid UUID; it is not guessed by the client.

An interrupted, malformed, timed-out or ambiguous response leaves the current step unknown and preserves its exact body/key in private tab memory. Explicit reconciliation resends only that step. A later 4xx, including 409/412/429, does not prove that an earlier uncertain request failed. A definitive 4xx on a step's first attempt may release that step. If contact creation is definitively rejected, the full form remains editable and no lead is sent. If contact is acknowledged but the first lead attempt is definitively rejected, retain the known saved contact, make contact fields read-only and allow a reviewed new lead attempt with current source/intent/timeline and a new key. The user may instead explicitly choose **Keep saved contact and close**; this performs no deletion or rollback and truthfully leaves a contact without an opportunity. Never offer that resolution while either step is unknown.

Use a conservative 23-hour retry window for each step from its first send, checked with both wall and monotonic elapsed time. Invalid/backward clocks fail closed. An expired unknown step stays unresolved and cannot be replaced, abandoned or assigned a new key in this slice. A contact-acknowledged lead that has never been sent may be reviewed against current context before its first attempt; if the original sequence is no longer acceptable, the known contact-only exit remains available. Neither client nor server promises indefinite deduplication after any future receipt deletion; durable key cleanup needs its own decision.

Contact and lead POST get a narrow command boundary before the generic mutation path. Reject undeclared query parameters. Before awaits, detach/validate the generated body, exact route, printable key and canonical legacy-compatible request hash. After the actor-scoped advisory lock, inspect a matching receipt regardless of expiry using current database time. A changed hash returns `idempotency_conflict`; an expired matching receipt returns `receipt_expired`; neither falls through to another insert or renews the receipt. Preserve historical rows created by the generic path: accept a null historical response ETag only after validating its generated body/status, but store `"1"` for new receipts. Preserve the existing one-day duration.

Both first execution and replay require `estate_runtime` as session/current user, matching transaction tenant/actor, active membership/role/organization, the exact complete current grant snapshot and current CRM entitlement. Recheck after advisory and row-lock waits with `clock_timestamp()`, and immediately before returning. Contact execution/replay requires current contact-write scope for the created contact. Lead execution locks and rechecks the referenced non-archived contact under the existing contact-write requirement, the effective owner membership and applicable actor/owner office links in stable order, the selected lead source, and the current first pipeline stage before insert. Lead replay locks/rechecks the receipt-bound contact and lead, current lead-write scope, effective owner/office relationship, source/stage references and CRM capability. Preserve own/team/organization rules; never substitute a different owner, source, contact or stage after waiting. Failed reauthorization rolls back domain/audit/event/receipt effects.

The UI owns one protected sequence state. Contact acknowledgement may advance to a generic lead-ready state while hidden/offline, but must not start the next request until current context, visibility, connectivity and busy guards pass. A valid lead receipt may acknowledge while hidden/offline; clear private sequence values and defer list/detail refresh until live eligibility. Historical receipts acknowledge commands but never become current workspace detail. After lead acknowledgement, refresh current lists separately and show acknowledged/current-unavailable honestly if that read fails.

Pending/partial sequence state protects dialog close, internal navigation, organization switch, sign-out, competing mutations and PWA reload. Unknown states keep all captured fields read-only. Offline/hidden pending views render generic status without private form/contact values. Access/context loss invalidates callbacks, clears private sequence state and does not claim failure or success. The persistent workspace layout retains the sequence across internal workspace view routes, but document reload remains guarded rather than persisted. No service worker, IndexedDB, URL, history state or other durable browser storage holds bodies, keys or contact values.

Backend owns contact/lead POST command preparation, receipt/authority/source locks and narrow main-route registration under `apps/api/**`. Frontend owns a new protocol/panel and narrow Add lead/shell integration under `apps/web/**`. Tester owns independent actual PostgreSQL/runtime-role API, protocol/controller and static React acceptance under `tests/**`. Root owns this decision, runbook/status, shared route review, retained regressions, compiled build/runtime/launcher probes and publication. Shared contracts, migrations and dependencies remain unchanged unless a new prerequisite is separately reviewed and committed.
