# ADR-046 — Recoverable Task update and completion

Accepted by the coordinating owner on 2026-10-11 after ADR-045 verification. This bounded M2 slice advances MOD-D-007, MOD-B-001/003, MOD-B-AC-3, INV-01/02/03 and MOD-K-006/007. It covers the complete frozen `PATCH /v1/orgs/{orgId}/tasks/{taskId}` operation and replaces the two competing client paths for Task drawer edits and quick completion with one recoverable command. Task creation remains the separate ADR-044 command. Reminders, browser/device acceptance and broader Task workflow completion remain separate gates.

Preserve the closed `TaskWrite` contract: required assignee, title, due instant and timezone; optional Lead linkage, description, priority and state; required `Idempotency-Key`, CSRF and `If-Match`; `crm.tasks.write`; and `200 Task` with a strong ETag. No query parameters are accepted. An omitted Lead, description, priority or state preserves the current value. Explicit `leadId: null` unlinks only after the old source is authorized, and an empty description explicitly clears the description. Preserve the legacy canonical request hash over the detached body and exact supplied `If-Match` spelling, including quoted, bare and leading-zero revisions, so existing unexpired receipts remain replayable. A syntactically valid original revision must be a supported positive safe integer and successful execution returns exactly the next version.

ADR-036 authorization remains normative for PATCH. The command never adds a Task-read prerequisite. Standalone updates require current scoped Task-write authority over the current Task and proposed assignee. A Task linked before or after the update additionally requires both current scoped `crm.leads.read` and `crm.leads.write` authority over every current, historical-receipt and proposed Lead, with its unarchived Contact. Omission or explicit unlinking cannot bypass the old source. This intentionally preserves the reviewed PATCH policy and does not transplant ADR-044's write-only Task-create source policy. Task read/list behavior remains unchanged.

The API owns one dedicated Task-patch boundary. Before any wait it detaches and validates the queryless route, closed body, printable key, raw original revision, complete verified authority context and normalized domain values. It retains the immutable request body and preserves exact legacy hash semantics. It serializes by tenant, actor, route and key, then inspects a matching receipt even when expired. A changed hash conflicts. A matching expired receipt returns `receipt_expired` without execution, renewal or replacement. Replay strictly validates a `200 Task` receipt, route Task identity, expected next version, contract shape, every field determined by the command, stored Task reference when present and strong ETag. Omitted historical values are contract-validated but cannot be reconstructed after later edits because the frozen receipt schema has no response digest and Task has no full version history; adding either requires a separate migration/contract decision. The client still compares every omitted value with its captured original Task before acknowledging. A legacy matching receipt with null ETag and/or reference is accepted only after the same historical validation.

Fresh execution and replay require the actual runtime role, matching transaction tenant/actor, active membership/role/organization, exact complete current grants and current CRM capability. Replay authorizes both the historical receipt and current Task because the receipt can disclose a previous assignee, link and private Task fields. Lock the current Task, deterministically sorted current/historical/proposed assignee memberships, Contacts before their bound Leads, then deterministically sorted office relationships. Recheck the original Task scope and linkage after the Task wait and repeat full authority, source, eligibility and database-clock checks after every observable wait and before returning. A source substitution, archive, reassignment, office movement, grant/capability expiry or receipt expiry denies without partial effects.

The current Task and proposed assignee must satisfy own/team/organization Task-write scope. Own scope can retain or assign only the actor. Team scope can use active members in the actor's currently authorized offices. Organization scope can use any active member in the organization. An omitted or unchanged disabled assignee is rejected. An authorized team or organization manager may explicitly repair a Task assigned to a disabled member only after the locked current Task remains in the manager's current Task-write scope and the replacement is active and eligible. Replay requires both historical and current assignees to remain active and eligible; it never uses an eligible proposed or current assignee to authorize disclosure of an inaccessible historical assignee.

Fresh execution normalizes the nonempty trimmed title and due instant while preserving the supplied supported named IANA timezone alias. Description is exact when supplied. Omitted optional values retain locked current values. It uses one compare-and-swap Task update and writes one audit plus one-day receipt in the caller transaction. Every actual transition from a non-`done` state into `done` appends exactly one database-time, references-only internal `task.completed` activity, including a standalone Task whose Lead is null. A `done` to `done` edit and a replay append none; a later genuine reopen and completion is a new transition and may append one new completion activity. Do not emit `task.due`, mutate a Lead or invent a Task-updated/completed outbox type. The approved event catalog has no such event; expanding it is a separate reviewed contract proposal. Task, optional completion activity, audit and receipt commit or roll back together.

The PWA owns one `TaskEditProtocol` and controller for both drawer saves and agenda completion. Quick completion constructs `state: done` from the verified current Task, then enters the same command path. Drawer save captures due conversion exactly once and preserves the original instant, precision and timezone alias when the displayed field is unchanged. Before the first await both paths capture the exact serialized TaskWrite bytes, UUID key, raw original ETag and verified user/organization/member/CSRF/access-revision/full-grants binding. Task creation and Task update commands are mutually exclusive while either is unresolved.

An ambiguous outcome retains the immutable command and blocks competing Task commands, route changes, organization switch, sign-out, detail close and service-worker activation. Explicit reconciliation resends the exact bytes, key and original `If-Match` for at most 23 hours under both wall and monotonic clocks. A strict matching `200 Task`, next-version ETag and every resulting field acknowledge only the historical update. A separate authorized current Task GET supplies display state; reassignment or linked-source access loss may make that read unavailable without reversing the acknowledgement. A definitive initial non-timeout 4xx releases the command, while a rejection after an unknown attempt does not prove nonexecution. `401`/`403`, verified binding loss and organization changes synchronously clear private Task state and invalidate late callbacks. Offline, hidden and generic recovery states withhold Task, Lead, assignee and timing details.

ADR-042 local forgetting extends to an expired or clock-invalid unknown Task update with the exact action **Clear this tab’s recovery data**. It sends no request, removes all private command and draft values, invalidates callbacks, releases lifecycle guards, retains a generic warning and blocks another Task PATCH through the same controller binding. A context replacement or document reload may permit a human attempt and cannot prevent a possible duplicate. Forgetting never changes the acknowledged current Task or fabricates a command outcome.

Backend owns a new Task-patch command boundary plus bounded service/route integration under `apps/api/**`. Frontend owns the unified protocol/controller/panel and Workspace integration under `apps/web/**`. Tester owns PostgreSQL/RLS, protocol/controller/transport/static and integrated acceptance under `tests/**`. Root owns this ADR and integration review. The generic Task update port must fail closed once the dedicated route is registered. No migration, dependency, public-contract amendment, new event type or provider behavior is approved.

Acceptance covers optional preservation and explicit clears; exact hashes/revisions; same-key concurrency and distinct-key compare-and-swap races; expired, legacy and corrupt receipts; historical replay after later edits; safe revision exhaustion; own/team/organization scope; foreign/disabled/current/historical assignees; current/historical/proposed Lead and Contact sources; omission/null-link bypass attempts; actual advisory, Task, member, Contact, Lead and office waits; membership, grant and CRM expiry; pool reuse; rollback; exactly one completion activity for each genuine transition and none for replay or `done` to `done`. Client acceptance covers drawer/completion contention, exact immutable resend and due-time capture, strict acknowledgement versus current refresh, source/assignment scope loss, malformed error transport, initial rejection versus unknown outcome, dual clocks, forgetting, stale responses, context cuts, navigation/update protection and generic private-safe rendering. A fresh-database integrated flow proves manager capture, assignment, Agent Task creation, drawer edit, completion and stage transition while historical retries preserve current rows and activity counts. Retain Task creation, agenda, Lead assignment and stage-transition behavior. Browser/axe/keyboard and physical installed-mode behavior remain open.
