# ADR-019 — Synthetic support context and read-only CRM access

Accepted bounded MOD-A-006 implementation contract on 2026-10-10, before dependent consumers. This extends ADR-017's separate synthetic staff authority. Production support identity and live customer access remain gated. Frozen OpenAPI request/response bodies and generated types stay unchanged.

Grant creation uses the frozen AccessGrant body and returns a frozen Job. Business validation requires a nonblank reason of at most 1,000 characters, one to seven unique catalog CRM read permissions and an active synthetic recipient. Expiry is fixed at creation from the database clock, at most one hour, and replay cannot renew it. Related records require their own read permissions. Grant and revoke Jobs use kinds `staff.support.grant` and `staff.support.revoke`. Requester-only command recovery returns the current authorized grant reference through the internal SupportAccessPort, without making that reference permission evidence.

Grant create and requester support Job reads expose `X-Synthetic-Support-Grant-Id` (UUID) and `X-Synthetic-Support-Grant-ETag` (a quoted positive safe integer). The standard Job ETag, when emitted, is separate transport metadata. The frozen Job has no version field; clients cannot compare the Job ETag to an invented body version or use it to revoke a grant. Revocation requires the grant's original strong If-Match value and an idempotency key. Exact successful replay preserves the original outcome; changed command input or an unrelated stale revision fails safely.

Local staff session reads and support selection/clear remain under `/dev/staff/`, with explicitly enabled synthetic mode and actual loopback. All responses are private/no-store and contain only the closed synthetic staff session or frozen bodies. Session responses expose `X-CSRF-Token` and `X-Synthetic-Support-State` (`none`, `active`, or `stale`). Active context includes its purpose, expiry, organization and permitted reads, matching the grant metadata headers. None/stale responses contain `supportContext:null` and no grant metadata; stale preserves verified staff identity with a warning, without disclosing an inaccessible grant. Staff sessions have no row revision, so these routes introduce no Session ETag or If-Match requirement.

Selection and clear require CSRF, same-origin validation and an idempotency key scoped to the exact opaque staff session. Identity verification takes that session's UPDATE lock from the outset for context mutations, avoiding SHARE-to-UPDATE upgrades. A replay after context changes returns a fresh currently authorized Session or an explicit conflict; it never reselects or clears a newer context. Login/logout and selected-grant expiry/revocation preserve this separation from member sessions. Selected contexts cannot provision or acquire tenant write authority.

Support reads recheck the active principal, exact current opaque session, selected recipient-bound grant, active organization, current CRM entitlement, permission catalog and database-clock expiry before and after projection. CRM owns the closed projections for contacts, leads, tasks, deals, pipeline stages, lead sources and tags. Notes, exports, mutation commands, consent, billing and provider effects remain unavailable. Forward SQL must prevent permissive provisioning policies from composing into active-organization writes and permit only narrow source locks. Clearing an expired, revoked or stale context needs separate append-only control command evidence tied to the exact own session; it must not invent a tenant audit grant or fake Job.

Browser helpers validate the approved closed bodies and headers, retain uncertain commands' original key/body/If-Match, and keep context only in memory. An opaque local session generation changes on login, logout, identity/CSRF change or definite identity loss. A separate response sequence prevents older reads or selections from replacing newer current context. Dirty or uncertain work remains protected during navigation and PWA updates; private support data never enters service-worker caches or persistent browser storage.

Acceptance requires real-login PostgreSQL RLS tests for forged context, missing/expired/revoked grants, read scope and related records, archived organizations, current entitlement, selected-context write denial, retained provisioning claims, exact own-session clear evidence, lock races, two-session idempotency isolation, changed-context replay, requester recovery and original expiry. Registered HTTP tests must also cover mixed identity cookies, CSRF/Origin, safe errors and private headers. Browser/physical-device acceptance remains separate and must not be claimed from static renders or API tests.
