# ADR-013 — Transactional synthetic capture and routing

Accepted for local implementation on 2026-10-10 after coordinator schema/migration review. The frozen v1 OpenAPI remains unchanged.

`packages/contracts/internal/native-capture-v1.schema.json` adds a bounded local capture command using generated LeadCreate contact/source/intent/timeline properties, a stable source submission UUID, and optional postal code. The corresponding CRM service port is bound to the verified context and caller's PostgreSQL transaction. A later form service can save its entry and invoke CRM through this port without directly writing CRM tables or creating a separate transaction. Source resolution, public visitor context and consent evidence remain prerequisites for public forms and inquiries.

Local `/dev/capture` requires explicitly enabled loopback development/test mode, a current synthetic session, CSRF, an idempotency key, active contact/source visibility and current CRM entitlement. Organization-scoped lead writing is required to route beyond the acting member. Body tenant/owner/member/site identifiers cannot grant access and are excluded from the command. It returns the frozen Lead shape; decision identifiers and safe reason codes may use development response headers.

Migration 0009 introduces tenant-scoped FORCE-RLS routing state, a serialized distribution counter and an immutable capture-decision ledger with composite tenant/source/lead/rule foreign keys. A tenant/source/submission identity binds a canonical request hash. Repeated commands create one decision, lead and event; changed input conflicts. Replays recheck current source permissions, membership, entitlement, archive and assignment visibility before returning the current authorized lead.

Rules run in ascending configured priority with a stable identifier tie-break; the fixture defaults place first-touch before listing attribution and round robin. First-touch considers the earliest active contact lead's owner and falls through when that member is ineligible. Geography uses the explicitly supplied, bounded postal code. Weighted round robin checks active tenant membership, current lead permissions and an office membership for team-scoped recipients, with distribution serialized in the database. A caller with any non-organization contact/lead grant is conservatively restricted to self-assignment. A trusted office-bound source resolver remains a prerequisite for public office-specific capture. Listing-attributed assignment returns an unavailable reason and continues to a permitted fallback until a verified attribution resolver exists. No live MLS request or fabricated listing-agent mapping is permitted. No eligible recipient leaves an organization-scoped opportunity unassigned with an explicit reason; restricted callers receive a validation failure instead of losing visibility.

Routing configuration preserves immutable rule IDs and uses an aggregate revision ETag. Removed rules remain immutable history references, disabled and marked retired, with negative internal priority positions freeing current public slots. Disabled current rules remain part of configuration. Retired IDs cannot silently reactivate; restoration requires a future explicit command. Internal retirement metadata is never a client authorization claim.

The frozen replacement command contains neither rule ownership nor an office target. Whole-organization replacement therefore requires organization-scoped `crm.routing.manage`; own/team replacement fails with `routing_scope_unavailable`. Routing reads project recipients to the caller's own or shared-office visibility, omitting weighted rules without visible recipients. `X-Routing-Can-Replace` is true only for organization-scoped read and manage grants; every write still rechecks current permission. A future scoped replacement contract requires explicit review before enabling own/team writes.

Each new synthetic native inquiry receives ten points under `synthetic-native-inquiry-v1`; replay returns the same lead without increasing its score. Distinct submissions currently create distinct leads rather than accumulating engagement on one opportunity. Manual opportunities remain unknown. The score is only a deterministic follow-up indicator; no protected attributes, housing eligibility or financial decisions are inferred. Production engagement scoring, event reconciliation and UI reason/time readback remain later acceptance.
