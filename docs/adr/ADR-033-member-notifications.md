# ADR-033 — Member-owned notification center

Accepted by the coordinating owner on2026-10-10 after the user resumed implementation. This bounded M2 slice implements MOD-B-005 and uses the existing frozen Notification/PageNotification schemas, GET /v1/orgs/{orgId}/notifications and POST /v1/orgs/{orgId}/notifications/{notificationId}/read. No public contract, migration, dependency, provider or publication change is authorized by this slice.

NotificationService in apps/api/src/notification-service.ts uses the existing verified tenant transaction and requires self.notifications.read/write. Every read and mutation also binds tenant_id and member_id to the verified context, even for organization-scope grants. Own membership is the authority; request identifiers and notification links are not. Current membership/role checks precede historical idempotency replay. Mutations lock the owned notification before using the existing foundation idempotency/audit conventions. First marking read persists the database timestamp and increments its row version; retries and later keys preserve the original timestamp and produce no duplicate transition/audit. No lead, contact, task, consent or provider record is changed. No notification production event or delivery worker is introduced.

The service exposes list(query): PageNotification and markRead(id, key): ApiCommandResponse (201 Notification), plus an owned read helper only if useful internally. Pagination uses the existing opaque cursor binding with organization, actor/member, resource and permission scope; bound IDs use the repository's canonical UUID validation. Only contract cursor/limit queries and empty/no mutation bodies are accepted by the route. Invalid/foreign/member-mismatched identifiers are unavailable. The fixed safe payload projection accepts only bounded kind/title and an optional safe local path href; arbitrary payload keys remain internal and can never be returned or written to logs/audits. Invalid payload metadata is unavailable rather than fabricated. The existing foundation audit contains only resource identity/version and fixed transition action. Read-state changes are not public lead activity.

Frontend NotificationCenter owns new notification-center.tsx, notification-center.module.css and notification-controller.ts in apps/web/components, with generated API types only. Workspace integration is the frontend owner's narrowly scoped change to workspace.tsx. Props include current Session, accessRevision/member identity, online state and CSRF; each access/member/tenant change invalidates pending reads and command receipts. The controller retains an uncertain command's exact key in browser memory and explicitly reconciles it; no blind resend with a fresh key. Access denial clears member-private rows, pagination and pending command state. No private localStorage/IndexedDB/service-worker cache is added. Show distinct loading/empty/error/read/pending/uncertain states, keyboard-operable pagination/read controls and 360px layouts. Hrefs are restricted to same-origin local application paths and navigation respects existing dirty-draft protections.

Coordinator owns API route integration, seed decisions, contracts, dependencies, status, CI and combined verification. Backend owns only notification-service.ts (and a small service-local helper if necessary). Frontend owns the notification component/controller/style and the workspace integration. Test agent owns new tests/integration/notifications-api.test.ts and tests/unit/notification-controller.test.ts, plus a new component test if supported by the established harness. Other existing feature owners and separate worktree chats are not automatically resumed.

Acceptance requires actual PostgreSQL/runtime-role HTTP tests proving member/tenant isolation, changed cursor context, missing/revoked permissions/membership, concurrent same/different key marking, historical replay, stable read timestamp, audit privacy and no underlying lead changes. Controller tests cover stale reads, access invalidation, offline denial, exact uncertain retry and bounded pagination. Combined source/contracts/typecheck/build and relevant retained regressions must pass. Browser/axe/physical-device acceptance remains a separate recorded gate; a passing server suite does not close M2 or M8.

Prerequisite review found that migrations0001–0019 create the table but grant runtime no access. The additive candidate docs/proposals/W03-notifications/runtime-access.sql precedes service execution. It grants only the required SELECT columns and UPDATE(read_at,updated_at,row_version), with restrictive runtime member/current-permission RLS in addition to tenant_scope. No INSERT/DELETE, payload/member writes or worker/control grants exist. A private trigger locks the current membership/role/organization, denies unread/repeated transitions and immutable metadata changes, stamps the first read with the database clock and increments one safe row version. Direct runtime access and pool reuse are required test cases. Coordinator allocation of reviewed forward0020 follows independent source review; no prior migration is edited.
