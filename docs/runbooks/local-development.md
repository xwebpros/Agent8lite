# Local synthetic application

Use Node 24.19.0 and pnpm 11.25.0. Run `pnpm install`, `pnpm contracts:generate`, and `pnpm contracts:check`. Start PostgreSQL/PostGIS and Redis with `docker compose up -d` when Docker is available. The development ports bind only to loopback.

On this Windows workspace, PostgreSQL 17.10 is supplied by the pinned optional `@embedded-postgres/windows-x64` package. Download the official OSGeo `postgis-bundle-pg17-3.6.2x64.zip` from `https://download-cache.osgeo.org/postgis/windows/pg17/`, verify its publisher checksum, and extract it into `.local/postgis/`. `pnpm db:local` copies the native binaries into `.local/postgres`, creates a persistent synthetic cluster in `.local/pgdata`, and listens at 127.0.0.1:55432. It never touches another PostgreSQL installation. Stop this owned cluster with `node scripts/local-db.mjs stop`.

Run `node --env-file=.env.example --import tsx packages/db/migrate.ts`, then `node --env-file=.env.example --import tsx packages/db/seed.ts`, then `pnpm dev`. Open `http://localhost:3000`. Development sign-in selects only a fixed fictional identity. Secrets in `.env.example` are conspicuously local test passwords, and production must supply separate migration/runtime identities and a verified OIDC configuration. The portable Windows tools need the normal user token; an execution sandbox may require the approved command escalation for PostgreSQL and `tsx`.

The application API uses the non-owner runtime role. Never run the API with the migration login. The original 72-table schema is preserved as migration 0001; reviewed corrections use forward migrations. Rerunning seed should preserve user-created synthetic records; do not reset a shared cluster to repair an application defect.

After migration0012, run `node --env-file=.env.example scripts/local-control-identities.mjs` to configure the distinct local control/issuer logins. SQL contains no passwords for these roles. The tool requires explicit synthetic mode and same-loopback role URLs, configures only previously unset passwords and verifies the exact login; it preserves existing passwords and fails safely if the supplied credentials do not match. Never share migration credentials with runtime, worker, control or identity issuance pools. Staff/provisioning HTTP consumers remain gated until their integration acceptance passes.

Run `pnpm typecheck`, `pnpm lint`, `pnpm test`, and `pnpm build`. `pnpm db:verify-fresh` creates a uniquely named loopback-only acceptance database, migrates and seeds it, verifies RLS roles/PostGIS, reruns migrations for checksum stability, and removes only that disposable database. E2E uses `pnpm test:e2e` through the repository's Playwright harness when browser access is permitted. Browser/device tests do not establish feed rights or production readiness. iPhone/Android require an authorized HTTPS staging origin for actual home-screen installation; loopback development validates browser behavior only.

Use `pnpm test:isolated` for repeatable local non-browser acceptance without changing the interactive application's database. Each integration suite gets a separate disposable database, private-object directory and API process, keeping production request-rate limits intact and preventing fixture leakage between suites. The runner migrates/seeds, launches its API on an available loopback port, explicitly overrides runtime/worker/test URLs, runs Vitest and removes only its owned API, database and directory afterward. It aggregates the reports and treats skipped/failed tests as an incomplete acceptance run. Pass optional Vitest test paths for a bounded batch, for example `pnpm test:isolated tests/integration/data-transfer-api.test.ts`. PostgreSQL must already be running. Browser and physical-device acceptance are separate gates.

The web BFF uses server-only `API_ORIGIN` (default `http://127.0.0.1:3001`). It accepts only a configured HTTP(S) origin without credentials, path, query or fragment. Synthetic mode additionally requires a loopback API destination. This value never comes from a request or tenant content; production identity activation remains a separate gate.

The isolated runner generates a non-secret instance identifier for its API process and verifies the matching synthetic health response header before launching tests. A successful response from an unrelated process on a reclaimed port cannot satisfy readiness. The identifier is never sent in the readiness request and is exposed only in explicitly enabled synthetic development/test mode.

The worker runs with `node --env-file=.env.example --import tsx apps/worker/src/main.ts --once` for one PostgreSQL recovery pass, or without `--once` for the polling worker and optional BullMQ wakeups. Its reference consumer records immutable receipts and acknowledgments atomically; it does not send messages or execute later domain consumers. Recovery runs regardless of Redis availability. Redis stores only a closed version/context hash hint that resolves through trusted server configuration; it never establishes membership or permission. Unknown/malformed hints deny and producer commands do not buffer while disconnected. `WORKER_CONTEXTS`, when configured, is a JSON array of at most100 unique canonical `{userId,organizationId}` UUID pairs; no global tenant discovery is implemented. Keep this server-owned value out of requests and tenant content.

Do not run the worker alongside the outbox fault-injection suite, which briefly revokes an audit privilege to prove rollback. Disconnected Redis and real PostgreSQL recovery tests are separate from actual Redis loss/restart acceptance. The latter remains an unfinished gate until run against a dedicated disposable Redis service. No campaign or production-delivery scheduling claim follows from this reference consumer. See ADR-015.

No real email/SMS/push, Stripe transactions, DNS changes, live Trestle access or customer data are used. Production release remains subject to the TDD's M8 gates.
