# Local synthetic application

Use Node 24.19.0 and pnpm 11.25.0. Run `pnpm install`, `pnpm contracts:generate`, and `pnpm contracts:check`. Start PostgreSQL/PostGIS and Redis with `docker compose up -d` when Docker is available. The development ports bind only to loopback.

On this Windows workspace, PostgreSQL 17.10 is supplied by the pinned optional `@embedded-postgres/windows-x64` package. Download the official OSGeo `postgis-bundle-pg17-3.6.2x64.zip` from `https://download-cache.osgeo.org/postgis/windows/pg17/`, verify its publisher checksum, and extract it into `.local/postgis/`. `pnpm db:local` copies the native binaries into `.local/postgres`, creates a persistent synthetic cluster in `.local/pgdata`, and listens at 127.0.0.1:55432. It never touches another PostgreSQL installation. Stop this owned cluster with `node scripts/local-db.mjs stop`.

Run `node --env-file=.env.example --import tsx packages/db/migrate.ts`, then `node --env-file=.env.example --import tsx packages/db/seed.ts`, then `pnpm dev`. Open `http://localhost:3000`. Development sign-in selects only a fixed fictional identity. Secrets in `.env.example` are conspicuously local test passwords, and production must supply separate migration/runtime identities and a verified OIDC configuration. The portable Windows tools need the normal user token; an execution sandbox may require the approved command escalation for PostgreSQL and `tsx`.

The member notification center requires reviewed migration0020 and current self.notifications.read/write permissions. It lists only the active member's notices and marks them read through the frozen idempotent command; repeat marking preserves the first database timestamp. No default notices or notification producer are seeded. An empty center is expected until a supported workflow creates notices. Pending/uncertain read commands must be reconciled before switching organizations, signing out or accepting a PWA reload. Private notices and retry keys stay in tab memory; offline mutation is disabled. See ADR-033 for service/RLS and acceptance details. This authenticated feature is separate from the hosted demo.

The dashboard's stored appointment agenda requires migration 0021, current appointments.read and crm.leads.read permissions, and an active CRM capability. GET /v1/orgs/{orgId}/appointments returns only records linked to the current member's assigned, unarchived leads and contacts. Organization grants do not widen this list; a team-only CRM grant also requires current office membership. No appointments are seeded, so an empty agenda is expected until an approved producer exists. There are no booking/cancellation commands or calendar synchronization. Loaded pages are bounded to 200 records in tab memory and are not a complete daily agenda. User, organization and source timezone offsets plus explicit UTC references distinguish daylight-saving transitions. Offline, hidden or changed-access views discard private rows. Lead buttons respect the workspace's draft/unconfirmed-command guard. See ADR-035; this authenticated slice is separate from the hosted demo.

The dashboard's loaded task agenda groups currently fetched open tasks into overdue, due today and upcoming using one captured UTC instant and the explicit user timezone. Counts describe loaded records, with a five-row display bound per group and partial-pagination disclosure. Offset-aware user, organization and stored source labels plus UTC references distinguish daylight-saving overlaps. Invalid timing is unavailable; offline or hidden views do not display private task rows. This uses existing scoped task reads and adds no scheduler, task delivery or API shape. Linked tasks require current linked lead/contact access; reassignment, archive or lost team-office scope can make a task unavailable. See ADR-036.

The dashboard report uses the exact bodyless/queryless GET contract. Its leads.created definition version2 counts currently owned, unarchived leads created in the closed UTC month-to-captured-database-clock period, intersected with current lead permissions. Returned millisecond bounds also define the SQL measurement; source refresh is captured afterward. Reassignment and archive can change the count for a past creation period. This is not an acquisition-event/cohort metric. Larger role grants do not widen the default member scope, and unavailable capability/permission is denied rather than measured as zero. Revenue remains null/unavailable until a reviewed billing measurement exists. See ADR-037.

Reporting snapshots remain in tab memory with member/access binding and current visibility/online checks. A snapshot older than five minutes is explicitly stale; refresh reads the same approved source. These measured totals are separate from the workspace's partial loaded-list summaries and do not establish provider synchronization, complete dashboard coverage or module acceptance.

Run fixture-dependent integration files in separate disposable invocations. Explicit multiple paths passed to scripts/test-isolated.mjs share one database; retained suites can leave eligible source rows that invalidate another suite's fixture-specific totals. The default full runner allocates each integration file its own database. Reporting's reference-query reconciliation and file-fresh fixture expectations are distinct assertions.

Contacts search uses the server's case-insensitive literal display-name predicate, including records beyond the initial loaded page. Email and phone are displayed when available but are not name-search fields. My workspace adds the verified member owner filter; All permitted records still intersects current contact permissions. Search text and rows remain private tab memory. Pages are ID-ordered and bounded, with loaded/more labels rather than complete totals; source changes between requests can affect results. Changed query or scope resets pagination. Current access and CRM expiry are checked on each read. Earlier contact cursors may require a fresh search after the internal binding upgrade. No saved filters are persisted. See ADR-038.

ADR-039 defines contact-drawer PATCH recovery. An unconfirmed edit retains its original input, revision and key in tab memory; Reconcile contact save resends only that captured command, never current form values. A rejected reconciliation does not establish that the earlier edit failed. Successful historical receipts acknowledge the edit, then the drawer reads current detail instead of displaying the old receipt. Saving/reconciliation requires current contact read/write access and active CRM. Contact/source/office changes and expiry are rechecked after database waits. Primary channels are presented first from the stored primary flag, without implying verification or consent.

Contact reconciliation has a conservative 23-hour client window within the existing one-day server receipt duration. Invalid/backward clocks or an expired window disable resend and retain the unconfirmed outcome for current record review; they do not create a replacement key or prove failure. An existing expired contact PATCH receipt is denied without a new write. Pending edits protect navigation, organization switch, sign-out and application reload; offline/hidden views withhold private details. This does not implement the Add lead multi-stage create chain, generic CRM recovery or a new contact-update outbox event. Those remain separate acceptance prerequisites.

The workspace-only route-group layout preserves command state across internal workspace views and keeps demo/staff pages separate. If history changes the route during an unconfirmed save, Return to unconfirmed contact save returns to that command's original contact; it does not discard or resolve the save. A current detail read's access denial clears private authority state even while hidden/offline; source unavailability clears current details while retaining an uncertain command. An expired unknown outcome has no abandonment workflow in this slice. Document reload loses tab memory, so browser navigation/update protections and actual mobile behavior remain required acceptance checks.

An unconfirmed task completion retains its original task body, revision and idempotency key in tab memory. Use Reconcile task completion before navigating, changing organizations, signing out or accepting an application update. Retries preserve the original command and a rejected retry cannot prove an earlier uncertain attempt failed. Current access loss clears private command state. A validated completion receipt triggers a fresh task read rather than overwriting a newer task with a historical receipt. Editing a task without changing its displayed due field preserves the original instant, timezone and sub-minute precision; changed due fields use the displayed device-timezone policy and its daylight-saving resolution.

The application API uses the non-owner runtime role. Never run the API with the migration login. The original 72-table schema is preserved as migration 0001; reviewed corrections use forward migrations. Rerunning seed should preserve user-created synthetic records; do not reset a shared cluster to repair an application defect.

After migration0012, run `node --env-file=.env.example scripts/local-control-identities.mjs` to configure the distinct local control/issuer logins. SQL contains no passwords for these roles. The tool requires explicit synthetic mode and same-loopback role URLs, configures only previously unset passwords and verifies the exact login; it preserves existing passwords and fails safely if the supplied credentials do not match. Never share migration credentials with runtime, worker, control or identity issuance pools. Local staff/provisioning is now registered under ADR-018; production staff identity and support access remain unavailable.

Run `pnpm typecheck`, `pnpm lint`, `pnpm test`, and `pnpm build`. `pnpm db:verify-fresh` creates a uniquely named loopback-only acceptance database, migrates and seeds it, verifies RLS roles/PostGIS, reruns migrations for checksum stability, and removes only that disposable database. E2E uses `pnpm test:e2e` through the repository's Playwright harness when browser access is permitted. Browser/device tests do not establish feed rights or production readiness. iPhone/Android require an authorized HTTPS staging origin for actual home-screen installation; loopback development validates browser behavior only.

Use `pnpm test:isolated` for repeatable local non-browser acceptance without changing the interactive application's database. Each integration suite gets a separate disposable database, private-object directory and API process, keeping production request-rate limits intact and preventing fixture leakage between suites. The runner migrates/seeds, launches its API on an available loopback port, explicitly overrides runtime/worker/test URLs, runs Vitest and removes only its owned API, database and directory afterward. It aggregates the reports and treats skipped/failed tests as an incomplete acceptance run. Pass optional Vitest test paths for a bounded batch, for example `pnpm test:isolated tests/integration/data-transfer-api.test.ts`. PostgreSQL must already be running. Browser and physical-device acceptance are separate gates.

The web BFF uses server-only `API_ORIGIN` (default `http://127.0.0.1:3001`). It accepts only a configured HTTP(S) origin without credentials, path, query or fragment. Synthetic mode additionally requires a loopback API destination. This value never comes from a request or tenant content; production identity activation remains a separate gate.

The isolated runner generates a non-secret instance identifier for its API process and verifies the matching synthetic health response header before launching tests. A successful response from an unrelated process on a reclaimed port cannot satisfy readiness. The identifier is never sent in the readiness request and is exposed only in explicitly enabled synthetic development/test mode.

The worker runs with `node --env-file=.env.example --import tsx apps/worker/src/main.ts --once` for one PostgreSQL recovery pass, or without `--once` for the polling worker and optional BullMQ wakeups. Its reference consumer records immutable receipts and acknowledgments atomically; it does not send messages or execute later domain consumers. Recovery runs regardless of Redis availability. Redis stores only a closed version/context hash hint that resolves through trusted server configuration; it never establishes membership or permission. Unknown/malformed hints deny and producer commands do not buffer while disconnected. `WORKER_CONTEXTS`, when configured, is a JSON array of at most100 unique canonical `{userId,organizationId}` UUID pairs; no global tenant discovery is implemented. Keep this server-owned value out of requests and tenant content.

Do not run the worker alongside the outbox fault-injection suite, which briefly revokes an audit privilege to prove rollback. Disconnected Redis and real PostgreSQL recovery tests are separate from actual Redis loss/restart acceptance. The latter remains an unfinished gate until run against a dedicated disposable Redis service. No campaign or production-delivery scheduling claim follows from this reference consumer. See ADR-015.

No real email/SMS/push, Stripe transactions, DNS changes, live Trestle access or customer data are used. Production release remains subject to the TDD's M8 gates.

`pnpm dev` supplies distinct synthetic control/issuer URLs and fails safely if their existing passwords/configuration differ. `/dev/staff` provides a separate staff session and explicit reviewed local provisioning; the BFF selects the route's own identity cookie. Keep a pending Job ID for requester-authorized recovery. Reusing a run key reconciles its bound attempt; a fresh reviewed key is required to retry a failed or expired attempt. Phase1 UI cannot infer an expired running lease from the frozen Job body. No unattended execution or customer support impersonation is enabled.

Authenticated `/properties` uses the current synthetic native feed. Fixture ingestion/expiry remain their original timestamps: seeding does not renew stale records or undo withdrawal. Empty/unavailable listings later may indicate expired rights/data, rather than no inventory. `/websites` mounts site/document/revision selection and the native private draft editor. Start a blank draft or choose an explicit revision, resolve uncertain saves with the original key, and save/discard in the editor before leaving or switching organizations. Publication/Puck/recovery-index/domain/media/forms are unfinished gates. The mobile navigation scrolls horizontally to keep every view reachable with usable targets. The combined isolated runner also executes the control suite in its own separately named disposable database and includes CMS JSX source tests in its aggregate.
