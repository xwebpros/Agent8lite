# Proposal — bounded synthetic control plane and organization provisioning

Not implemented or accepted. Coordinator review/commit of the shared port, dev schemas, forward migration and ADR must precede consumers. Normative sources: MOD-A-001/006, MOD-A-005 failed-provisioning invariant, INV-01/03/06, MOD-J staff audit/replay requirements, frozen OrganizationCreate, AccessGrant, Job and staff permission catalog.

## Frozen API and identified gaps

Implement the original POST /v1/platform/organizations (OrganizationCreate → Job202), GET /v1/platform/organizations (PageOrganization), POST /v1/platform/organizations/:orgId/access-grants (AccessGrant → Job202), platform health/configuration and redacted platform audit reads. Preserve all frozen bodies. Plan writes are a subsequent bounded task; this proposal grants no control-role plan writes.

OrganizationCreate has no initial owner, verified onboarding identity, plan selection or billing approval. Do not create an Owner membership for the staff actor. Introduce a trusted BootstrapPolicyResolver that supplies a verified owner identity and an explicit synthetic provisioning policy; public body identifiers never select the owner or authorize a plan/capability. Initial local policy binds the existing verified synthetic owner fixture, synthetic-starter monthly plan, CRM/billing capabilities and no-charge/no-delivery provider modes. Coordinator must approve this policy. Production resolver remains unavailable: enqueue fails closed without approved owner/onboarding and commercial policy binding. Unknown Trestle, media, marketing, AI and external identity rights stay disabled.

There is no /v1/platform/jobs/:jobId route, and the tenant Job route requires membership that does not exist during bootstrap. Document this discrepancy. Reviewed loopback-only GET /dev/staff/jobs/:jobId returns frozen Job for its requesting staff principal; POST /dev/staff/jobs/:jobId/run accepts an empty object and explicitly runs this domain job. This is an operator-driven synthetic executor, not a live worker or a generic arbitrary-payload replay. Production staff Job polling needs a contract addition. Staff jobs use a control-owned durable table, not a forged requesting_member_id.

## Separate identity and context

Create a distinct estate_control database role: LOGIN, NOSUPERUSER, NOBYPASSRLS, NOINHERIT, NOCREATEDB, NOCREATEROLE, no application-table ownership or privileged reachable roles. Migration creates no password. Coordinator's local runtime/bootstrap tools supply a development-only password and CONTROL_DATABASE_URL; outside explicit synthetic mode an explicit URL is required. Reuse the reviewed startup role invariant. Migration and ordinary runtime/worker credentials never become control credentials.

Session issuance uses a second distinct login, estate_staff_issuer, owned only by the identity issuance seam. Its STAFF_ISSUER_DATABASE_URL is server configuration, never a browser field, and this synthetic issuer is unavailable outside explicitly enabled local development/test. It receives INSERT on only the immutable staff_session issuance columns, minimal verified issuer/subject identity resolution, and active-principal SELECT/row_version lock privileges. It has no session SELECT/UPDATE/DELETE, permission-code directory, platform or tenant reads, customer writes or control functions. Runtime, worker and control must not directly or indirectly reach this login, including NOINHERIT memberships that permit SET ROLE; issuer must not reach those roles. Migration and startup verify the ancestry boundary and reject mismatched configured login roles, in addition to the existing privileged-role/table-ownership invariant. No migration password or new HMAC/protected-key subsystem is introduced.

The identity module's StaffSessionIssuerPort accepts only the server token verifier's VerifiedOidcIdentity result after code/PKCE/nonce/issuer/audience/signature/expiry validation. Within its own short identity transaction it sets verified issuer/subject locally, resolves that exact existing email-verified identity, sets its resolved actor, locks the active principal FOR SHARE, rechecks source identity/current mode, generates opaque token/CSRF server-side and inserts an eight-hour session using the database clock. The INSERT policy repeats exact claim-to-identity/current-active-principal bindings, rejects selected support context and future-created/overlong sessions. No INSERT RETURNING or subsequent session read is needed; internal return values are the generated credential plus the known database-clock expiry. Raw browser identity IDs, auth GUCs or token bytes never invoke this issuance port. Issuer credentials are privileged only for verified issuance; isolating that pool is the explicit trust boundary. Database control credentials alone cannot mint a staff session by setting app.actor_id.

Staff identities are separately seeded verified subjects, staff-administrator and staff-support, under the existing synthetic RS256 issuer. They are not tenant members. Coordinator owns provider identity fixture additions. Administrator holds catalog platform codes; support holds organization/health/configuration metadata reads and can receive a support grant, but cannot issue grants or provision. Staff permission assignment remains migration/deployment-owned; no API edits staff_principal permission_codes.

Use a separate HttpOnly opaque estate_staff_session cookie and database staff_session. POST /dev/staff/session accepts {identity: administrator|support}, performs the same mock OIDC code/PKCE/nonce/signature/issuer/audience verification as member login, and is explicitly enabled development/test + actual loopback + Origin only. GET /dev/staff/session returns the reviewed internal session response and X-CSRF-Token header. POST /dev/staff/logout verifies Origin/CSRF and removes that opaque session. Every retained staff session lookup denies outside synthetic mode before database access, as member sessions do.

withStaffTransaction resolves the opaque session under token-hash RLS, sets the verified actor locally, locks the current active principal FOR SHARE and rechecks current catalog platform permissions. Database control authorization also requires the same current opaque-session hash, live session and current principal; setting an actor/tenant alone is insufficient. No browser actor/tenant/permission fields establish authority. A member cookie never authenticates /v1/platform; a staff cookie never silently becomes a tenant member. Explicit support selection stores its grant on the staff session. Selecting support clears or explicitly excludes member-cookie authority for customer routes; ambiguous contexts fail rather than combine grants.

Restrictive control-principal SELECT uses a direct live-session/hash/actor binding rather than recursively calling principal authorization. Without that session, forged actor/issuer/subject context cannot expose a staff or customer directory. Control identity columns exclude email/phone and permit only the approved synthetic Owner's ID/issuer/subject/display name/verified flag/version under current platform.orgs.provision permission. The local policy binds fixed owner UUID 20000000-0000-4000-8000-000000000001, issuer urn:estate:synthetic and subject owner; a browser selector cannot change it. A narrow UPDATE(row_version) privilege with current-bound UPDATE USING and WITH CHECK(false) enables FOR SHARE without allowing real identity updates. Existing permissive identity_write excludes control so it cannot accidentally combine with that lock policy. Owner identity stays SHARE-locked through execution and activation; resolver assertCurrent compares the retained owner version and verified flag. Unknown production owner policy still denies.

## Transaction-bound provisioning ownership

ControlProvisioningPort.enqueue creates one organization(status provisioning), queued control Job, durable command record and audit in one staff transaction. IDs and bootstrap policy/owner binding are retained in the durable Job. Same staff/key/canonical body returns that original Job after current authorization; changed body conflicts. Commands do not expire into duplicate organizations.

claim transitions a queued/eligible expired-lease running job to running with claim UUID, lease and attempt count in one committed transaction. Execution is constructed inside a separate verified provisioning transaction: require current originating staff authority and a live session, owned job/claim/current lease, exact organization still provisioning, current verified owner and approved policy. Set that derived tenant and claim locally. No nested transaction is started by a module port. The local executor orchestrates these explicit transactions; future background credentials/claim recovery require coordinator-owned worker integration and a distinct approved job authorization boundary. This proposal deliberately does not borrow a human cookie for unattended production jobs.

SaaS bootstrap owns organization, built-in role presets, initial Owner membership and business profile. CRM bootstrap port owns six stages (Uncontacted, Attempted Contact, Nurturing, Dead, Under Contract, Closed), default website-inquiry source, routing state and initial default first-touch/listing-fallback/owner-only round-robin rules. Billing bootstrap port owns explicit mock subscription/entitlements/provider connection defaults under the approved local policy. Stable per-organization seed identifiers prevent duplicate defaults on a retry. No module directly writes the other module's tables.

Execution inserts defaults, verifies required counts, active Owner and policy outcome, emits only safe reference/audit records, updates organization active and Job succeeded atomically. A failed seed transaction rolls back all defaults and activation. A separate verified transaction records failed/unknown Job with a fixed actionable safe error; organization stays provisioning. A payment/provider acceptance cannot make the organization ready. Lost execution/lease may be retried through the same reviewed domain claim and policy, never by replaying arbitrary payloads. Completion means core synthetic defaults are ready; external MLS, delivery and production billing remain unavailable.

Database Job insertion requires the target still provisioning, a queued/no-claim initial state and current requesting authority. control_can_seed requires both the exact running unexpired owned claim and target status provisioning. Activation uses that narrow seed predicate for UPDATE USING and the current-claim predicate for WITH CHECK; seeding stops immediately once the organization is active. Job success separately requires the same claim/lease and active target, and a succeeded provisioning Job cannot reopen. Existing active/suspended/archived organizations cannot receive bootstrap Owner memberships, role defaults or entitlements by creating or fabricating a provisioning claim, including legacy/admin-injected running rows.

Use existing frozen integration.state_changed event with producer control-plane, aggregate organization, related Job UUID and an approved safe code; no organization name, owner email, reason, session/proof token or provider payload. Normal CRM capture and consent ports remain separate from bootstrap.

## Reasoned grants and customer access

Frozen AccessGrant selects an active staff recipient, a nonempty unique subset of the initial read allowlist, a trimmed nonempty reason and future expiry no more than one database-clock hour. Allowlist: crm.contacts.read, crm.leads.read, crm.tasks.read, crm.deals.read, crm.pipeline.read, crm.sources.read, crm.tags.read. No writes, consent changes, exports, billing commands, notes/message body access, impersonation or owner status. Catalog platform.support.grant authorizes issuing this constrained grant; it is not a tenant role permission. Recipient existence/current active state is resolved through the narrow reviewed DB helper, not arbitrary supplied staffUserId authority.

Create an immutable grant binding (tenant, recipient, issuer, read permissions, reason, expiry, synthetic provenance) and requester-scoped succeeded control Job atomically. Exact replay returns the original expired/revoked grant Job without renewing it. New grant requires a new reviewed command. Initial provenance is synthetic-local and is denied for both new and retained grants outside explicitly enabled synthetic mode. Legacy grants with no provenance/issuer are denied, not assumed trusted.

POST /dev/staff/support-context accepts {organizationId, accessGrantId}; verify current recipient, tenant, grant permissions, expiry/revocation and principal, then retain the selection on that staff session. DELETE/clear equivalent is POST with both nullable fields or a separate empty clear command in the reviewed helper schema. The proposal uses a separate POST /dev/staff/support-context/clear empty command. The response uses the internal staff session shape. Expose X-Staff-Session:true, X-Support-Access-Grant and X-Support-Access-Expires-At on authorized customer reads, with a visible application banner including purpose and expiry. Header/context selection never authorizes by itself.

Reviewed local revoke POST /dev/staff/access-grants/:orgId/:grantId/revoke accepts {}, CSRF/idempotency and If-Match. Recheck platform.support.grant, update revoked_at/version, audit and return Job202. No frozen grant revocation route exists; record the production contract gap. API, source reader and any future worker recheck current grant/principal/expiry; a retained selection or cached response is not permission evidence.

SupportCrmReadPort receives a verified SupportReadContext, not TenantContext, and is owned by CRM. Initial consumers are original contacts/leads/tasks/deals/stages/sources/tags GET list/detail routes only. Full grant scope is the explicitly selected organization because AccessGrant has no own/team scope model. Related source permissions are intersected: lead queries require contact read; deal queries require lead/contact read and deny archived related leads; task lead references require lead/contact read. Preserve current CRM entitlement checks initially; diagnosing disabled capabilities can use control metadata, not an invented commercial exemption. Notes and exports stay unavailable to support until separately reviewed.

Take SHARE locks on principal/session/selected grant in deterministic order, derive tenant only after validation, and recheck grant expiry immediately before commit/response. Read cursors bind staff principal/grant IDs and versions, current permissions, tenant/filter/sort/expiry. Each customer read emits a safe audit with staff actor, grant UUID, affected resource or list reference, trace and purpose reference; never the raw reason or private record body. The CRM port checks current grant before and after source projection. Source edits observed during a read cause stale/unavailable output instead of returning cached unauthorized data. A minimal entitlement row_version UPDATE grant exists solely for FOR SHARE when checking current capability; capability state itself is not writable by the support reader.

Database control role has no CRM writes. Reviewed restrictive SELECT policies require the current active recipient grant for each source table even if a tenant GUC is forged. Without selected/current grant, no CRM rows are visible. Existing runtime/worker tenant policies and grants remain intact. Selected grant does not authorize public visitor, marketing transport, worker send or arbitrary tenant commands.

## Acceptance and gates

Verify real role startup and missing-context RLS; member cannot access platform, ungranted/expired/revoked/inactive staff cannot read customer data, forged tenant/grant/recipient denied, session mode/socket/CSRF boundaries and visible banner. Verify grant read-only allowlist, exact replay never renews, principal/grant revocation races, safe platform audit projection and source revision/cursor binding.

Verify one queued organization/Job per concurrent command, body conflict, current permission replay denial, exact stable defaults and one non-staff Owner, caller rollback, failed seed leaves no defaults and no active organization, lease recovery/retry and current owner/policy revocation. New owner can select the ready organization through the existing member session; first capture works through CRM defaults. Billing/provider failure never activates it. Prove no live calls, actual charges, messages or licensed feed data.

Required coordinator decisions are reviewable implementation choices: approve local bootstrap owner/plan/capabilities, narrow helper security-definer role check and fixed search_path, control role/pool/tool integration, shared support context/CRM port and dev route schemas. Production OIDC/onboarding/merchant rights, automatic control worker and missing platform Job/revocation contracts remain explicit gates, not credentials inferred from this local slice.

## Candidate database verification

The coordinator authorized candidate execution exclusively in a uniquely named disposable loopback database. The reproducible verifier is verify-control-plane.mjs; run `node --import tsx apps/api/proposals/verify-control-plane.mjs`. It migrates 0001–0011, seeds synthetic fixtures, applies this candidate only there, verifies checksum replay and executes 15 real-login database probe groups. It removes only its own generated database, temporary role, and control/issuer roles if this invocation originally created them. Existing control/issuer roles require explicitly configured URLs; the verifier never changes an existing role password. It prints fixed check names/SQLSTATEs and writes safe evidence to control-plane-verification.json.

The latest evidence reports all 15 groups passed, including issuer-to-active-principal binding, blocked direct-control session minting, NOINHERIT ancestry rejection, grant/principal/session revocation and row-lock races, immutable grant expiry/permissions, irreversible revocation, current-clock grant/claim expiry, replaced claim denial, transaction rollback of attempted SaaS/CRM/entitlement/audit/event writes, FORCE RLS and preserved member identity/tenant access. A real PostgreSQL issue was found and corrected before this result: FOR SHARE also consults UPDATE USING policies. Narrow principal and recipient-grant lock policies now use current-bound USING with WITH CHECK(false), so row locks work while actual unauthorized updates remain denied.

The expanded evidence also contains 12 direct/multi-hop ancestry probes, active/suspended/archived target bootstrap denial, after-activation and completed-claim seed denial, forged/no-token identity-directory denial and approved-owner version/verified-flag lock races. All forbidden control↔runtime/worker and issuer crossings are checked recursively; the verifier grants temporary parent roles only to its control/issuer recipients, preserving existing runtime/worker authority.

This is database evidence for an unapplied shared proposal. The live estate database and API were untouched. Verified OIDC issuance consumers, HTTP mode/socket/CSRF/banner behavior, application command replay, full six-stage/bootstrap policy acceptance and execution recovery remain unimplemented gates; the existing 256-test application acceptance does not include this candidate.
