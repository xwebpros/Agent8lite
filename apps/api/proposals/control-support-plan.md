# Reviewed control support: bounded phase 2 plan

Read-only proposal, 2026-10-10. Sources: normative MOD-A-006/acceptance and MOD-J-002/003 in `docs/tdd/technical-design.json`; frozen `createSupportGrant` and `AccessGrant`; committed `control-plane-port.ts`, `synthetic-staff-v1.schema.json`, migration 0012 and ADR-017. Phase 1 remains source-stable. No database probes, shared role changes, new migrations or consumer edits were performed for this review.

## Bounded outcome and ownership

Implement reasoned, recipient-bound, at-most-one-hour synthetic support grants; explicit selection/clear; irreversible versioned revocation; and a CRM-owned read port for the seven already reviewed resources. Staff sessions remain separate from member sessions. Grant authority never becomes an Owner membership or a fabricated tenant `TenantContext`.

Control owns grant/session-selection commands and safe audit references. CRM owns projection/query behavior behind `SupportCrmReadPort` on the same caller client and verified `SupportReadContext`. Existing `CrmService` cannot be reused by fabricating a member or converting platform permissions to tenant grants. The ordinary tenant transaction requires membership and is deliberately unsuitable here.

Customer writes, notes/activity bodies, exports/imports, consent, billing, provider operations, attachments, CMS/MLS and any other resource remain unavailable. This is neither production staff identity nor a generic impersonation/replay facility. An unattended worker has no grant-read port or control credential; worker support access stays denied until independently reviewed.

## SQL and shared seams already available

| Operation | Existing reviewed boundary | Consumer obligation |
| --- | --- | --- |
| Verify staff identity | Separate issuer; active opaque session/principal; expected roles/recursive separation | Retained-mode/socket checks, current principal/session locks, current catalog code and expiry |
| Create grant | `control_grant_insert`, `control_staff_recipient_active()` | Current `platform.support.grant`; exact closed AccessGrant; locked active recipient; nonempty reason; distinct permitted read codes; database-clock expiry <=one hour; no implicit extra permission |
| Read grant metadata | `control_grant_read` | Explicit tenant/id and recipient or current grant-issuer authority; avoid any broad directory |
| Select/clear | Session UPDATE privilege only for selected tenant/grant, bound to exact actor/hash | Resolve recipient-owned grant from database, never use supplied tenant/grant as authority; lock own session before changing context |
| Revoke | Current grant authority, limited revoked_at/version/updated_at columns, revoked rows excluded | If-Match, grant row lock/CAS, permanent revocation; exact replay does not resurrect or extend |
| Read customer rows | `control_grant_allows()` and restrictive per-resource SELECT policies | Same client; verified selected context; explicit tenant predicates; related-source permissions, active CRM capability, organization status, resource archive predicates |
| Hold source grant | `control_grant_lock` permits FOR SHARE, WITH CHECK(false) | FOR SHARE rather than KEY SHARE, so a concurrent revoke waits through the projection commit |
| Hold capability | Entitlement SELECT and row_version UPDATE privilege with grant-bound policy | FOR SHARE, enabled CRM/clock expiry before and after projection; no entitlement state changes |
| Audit support action | Immutable audit INSERT under an owned support Job or currently valid selected grant | Fixed action/resource IDs/versions/trace only; no reason text, CRM body, token or unrestricted data |
| Durable result/recovery | `control_job` support kinds and `control_idempotency` | Atomic command→grant/job/audit binding, no terminal-key crash window or grant renewal |

The narrowly reviewed recipient helper locks an active target principal and returns only a boolean. Its definer executes only for an actual control login with a current grant-management session; no client-created claims or staff directory projection are needed. Grant issuance must call this helper inside the same transaction and hold its lock through commit.

## Current-source gap requiring coordinator decision

Migration 0012 permits organization SHARE/UPDATE row access only for a claimed provisioning organization. A support reader of an ACTIVE organization cannot use that policy to hold the status source stable. The organization SELECT policy also requires a platform metadata code, while the recipient helper only requires an active principal; a valid grant recipient with no metadata code would therefore have inconsistent capability/status resolution.

Recommended narrow forward correction, reviewed and committed by the coordinator before consumers: grant-bound organization SELECT for only `id=app.current_tenant()`, and a grant-bound active-organization lock policy whose actual UPDATE WITH CHECK is false. The existing limited organization UPDATE privilege suffices for the SHARE lock; add no new status-write privilege. This preserves provisioning activation and permits recipient reads without inventing an unrelated metadata permission. The selected grant/session helper has no organization dependency, so this policy can avoid recursive organization authorization. Exact policy and real-role probes need shared review; this file is not an approved SQL migration.

Independent read-only review identified two additional SQL prerequisites for that forward correction:

1. **Entitlement lock must prohibit actual UPDATE.** The committed restrictive policy `control_entitlement_lock` currently uses `app.control_grant_allows('')` for both USING and WITH CHECK. Together with the existing permissive tenant policy and `UPDATE(row_version)` privilege, a selected support reader can perform an actual row_version UPDATE; the column grant is not a lock-only boundary. The reviewed forward change must retain grant-bound USING for FOR SHARE and set a restrictive actual UPDATE WITH CHECK(false). Bootstrap only INSERTs entitlements, so this restriction does not need a bootstrap UPDATE exception. Do not rely on an additional permissive false-check policy to override an existing positive check.
2. **Organization locks must not compose into bootstrap writes.** A new permissive selected-grant active-organization lock policy, even with its own WITH CHECK(false), can have its USING OR-combined with the old `control_org_update` WITH CHECK. If the actor still holds an owned, current provisioning claim, the old check permits active status and can authorize an actual update to the newly ACTIVE organization through the new policy's USING. Add a restrictive organization UPDATE write check that denies any selected support context, while permitting the reviewed provisioning path only when the current verified opaque session has no selected tenant/grant. Inspect the exact current session selection, not merely a caller-set support GUC or whether the selected grant remains eligible. Keep its USING compatible with support FOR SHARE; denying selection in USING would remove the required lock. Preserve the unselected queued/running/provisioning activation case. Actual restriction SQL requires shared owner review before consumers.

These are database role-boundary requirements even though the phase-1 application rejects selected support sessions. API checks do not substitute for the direct SQL guarantees. No SQL change or probe has been executed in this proposal-only follow-up.

Current grant RLS enforces grant authority but does not itself require active CRM capability or filter archive/related-parent state. The proposed application reader must enforce those explicitly. Resource rows can use the same single-statement active-source projection semantics as ordinary CRM reads; it must never return a task/deal whose associated lead/contact is archived. If stronger resource-row SHARE locks are required, SELECT-only control privileges are insufficient and each minimal lock privilege plus restrictive UPDATE WITH CHECK(false) needs a separate reviewed forward correction. Do not grant broad CRM UPDATE merely to take locks.

## Request and result boundaries requiring approval

The only published command is frozen `POST /v1/platform/organizations/{orgId}/access-grants`: AccessGrant ->Job202, CSRF/Idempotency-Key. Business rules strengthen the permissive frozen string/array schema: one to seven unique allowlisted read codes, nonblank <=1000-character reason, live active recipient, known organization, and absolute requested expiry within the database-clock hour. Do not clamp or renew the user's expiry, silently add related-source permissions, or fetch anything from the reason.

Existing closed local schemas already cover `SyntheticSupportSelection {organizationId,accessGrantId}`, `{}` and `SyntheticStaffSessionResponse`. Suggested local selection/clear/revoke routes can consume those schemas without a new public body, but exact path/header registration belongs to the coordinator. Every local mutation must retain Origin/CSRF/idempotency; revoke additionally requires If-Match. No new public GET/DELETE access-grant endpoint is proposed.

Frozen Job omits the created grant ID, and selected Session omits grant version. A local caller consequently needs a reviewed response-header seam: `X-Synthetic-Support-Grant-Id` and grant `ETag` on grant creation and requester Job read; ETag for a valid selected context on Session/select. These are resource references, not secret authorization tokens. If omitted, creation cannot reliably lead to selection/revocation after interrupted commands. Grant-directory/detail UI remains a contract gap; do not invent a public grant listing. Requester Job read can recover the originally created grant reference/version for its creator under the correct kind-specific current permission, with explicit requester predicates even when health RLS sees broader jobs.

Session identity verification must allow invalid/stale selected contexts to be cleared or logged out. Recommended GET Session remains200 for a valid identity with `supportContext:null` when selection is no longer eligible, plus a reviewed safe selection-state header if UI needs to distinguish stale selection; CRM reads independently deny. A stale selection never silently switches organization or renews a grant. Actual valid Session supportContext supplies the banner's organization, reason, permissions and exact expiry. Frontend must clear current customer caches/drafts on selection changes and show the banner on every support projection; personalized data stays private/no-store and outside PWA storage.

Support selection is inherently a context mutation rather than grant creation. `SupportAccessPort.select/clear` currently have no key argument; bind durable command identity in the authenticated adapter/service wrapper or request an additive shared port revision. Replaying an old selection key after a later switch must not restore the old context or return stale-context data: return the current verified Session or a reviewed409 requiring refresh. Exact-key replay must never renew grant expiry. Logout continues to revoke the opaque session; stale credentials cannot obtain customer data.

Selection/clear command identity must additionally bind the exact opaque session, not merely staff user/route/key. The same staff principal may have multiple simultaneous sessions. Namespace the existing ledger route_key using a server-derived session-binding digest (within its 255-character bound), never a browser-supplied hash or a public URL/header. Keep this internal binding out of logs/traces. Lock the exact own session FOR UPDATE **before** command lookup/replay. Same-key retries in that session reload the current Session or return the reviewed 409; they never apply cached selection, cached reason or old tenant. Reusing a client key in a different opaque session is a separate context command and cannot reveal or alter the first session's selection.

**Clear audit prerequisite:** migration0012's restrictive audit INSERT policy permits an owned support Job or a currently eligible selected grant. After selection is cleared, or when its grant has expired/revoked, a recipient's ordinary clear cannot satisfy that policy. Do not require an eligible grant, invent an unrelated/fake Job, or let a failed audit make identity-only clear unusable. Recommended narrow shared review: support an exact own-session-clear audit **before** the selection UPDATE in the same transaction. The policy/helper must verify the current live opaque hash/actor, exact selected tenant/grant still present in the locked own session and a preserved grant belonging to this recipient; grant eligibility/expiry/revocation is intentionally not required for clearing. Bind the audit tenant/resource to those exact current session references, fixed clear action/type, attributable actor and a strictly safe empty/reference diff. A caller-set previous-tenant/grant GUC is not evidence. Audit and clear commit or roll back together. Because the existing INSERT guard is restrictive, the approved own-clear exception must be incorporated there; a new permissive policy alone cannot override it. No authority to query other customer records follows from this exception.

An unselected clear is an identity-only no-op and may be recorded in the existing immutable session-bound control command ledger without fabricating a tenant event. For malformed/foreign-recipient selected references, tenant audit must remain denied even though clear must stay usable. The coordinator may choose an immutable control-command audit seam for all selection/clear commands instead; its durable actor/session/route/trace and safe outcome would avoid a tenant Job or eligible-grant dependency entirely. Either exact pre-clear own-recipient audit plus safe control no-op evidence, or a reviewed immutable control-command audit design, must be approved before consumers.

## Transactions, locks and recovery

1. Verify enabled synthetic mode before pool use and actual direct loopback before any route; verify identity solely from the opaque staff cookie. Require the expected control login and no forbidden role ancestry. Verify mutation Origin and CSRF before state changes.
2. Lock current principal first. Read-only requests lock own session FOR SHARE; select/clear/logout must lock own session FOR UPDATE from the outset, avoiding two concurrent SHARE-to-UPDATE upgrades. Do not first take SHARE and later upgrade selection in a nested service.
3. Grant creation/revoke holds the issuer's session and current grant-management permission. Sort any additional recipient-principal locks deterministically; self-recipient should reuse the already locked principal. Cross-recipient grant issuances must not introduce reciprocal principal SHARE/UPDATE cycles.
4. For selection, update the exact own session only after resolving a same-recipient grant. Set transaction-local tenant/support-grant GUCs from the just-verified selection, then lock/reload grant and capability sources. A rejected selection rolls back entirely. Clear needs identity authority only and works even when the old grant is expired/revoked/unknown. Its approved audit is derived from the locked own session and committed atomically; it never borrows an unrelated Job or cached context.
5. Reader lock order: current principal -> own session -> selected grant -> selected organization (after reviewed gap fix) -> CRM capability rows in deterministic order -> one CRM projection. Grant/source expiry uses clock_timestamp, including rechecks after any lock wait. Recompute context before and after projection; never trust caller context permissions/provenance/state booleans. Reject changed principal/grant version, selected IDs, actor, current mode, expiry, organization or entitlement; discard projection before responding.
6. Grant creation atomically inserts grant, succeeded support-control Job, audit and immutable command record. It does not need an asynchronous claim because it has no provider/tenant bootstrap side effects. Command replay requires current issuer permission/requester, original hash, original grant identity/current eligibility and no expiry renewal. Expired/revoked source replay must not appear as an active usable grant; exact safe status is a coordinator decision.
7. Revocation atomically sets revoked_at/version with a current bound timestamp and creates its durable Job/audit/key. Replays recheck issuer authority and return the original revocation result without changing timestamps. Missing/stale If-Match fails before a fresh revoke. Do not clear recipient sessions as part of revocation: their stale selected references are harmless once grant policies deny and can be explicitly cleared, and locking other sessions would introduce additional deadlock paths.

`SupportAccessPort.assertCurrent(context, permission)` reloads the selected session/grant and returns a fresh verified context. It ignores supplied permission/provenance values, compares source identity/version to the caller's snapshot and denies unknown sources. Current recipient principal and session must remain active and live even if the stored grant is syntactically valid. Staff authority does not derive from organization membership, role presets, grant UUID knowledge or a client context header.

## CRM-owned read implementation

Use a separate read-only adapter in the owning API CRM area with only the seven typed resource names. It receives the already verified same client plus a current SupportAccessPort. No dynamic unallowlisted table/column interpolation or generic executable filter.

- Contacts: contact read grant; active unarchived contact; only active typed channels in the frozen Contact projection. No raw history/message bodies.
- Leads: leads +contacts read; unarchived lead and contact. Sources/stages are opaque IDs unless their separate read grants permit the separate endpoint.
- Tasks: tasks read; unlinked task is permissible; linked task requires leads+contacts read and current unarchived parent. No partial row or invented empty owner fallback.
- Deals: deals+leads+contacts read; current unarchived lead/contact. No projected deal outside parent visibility.
- Stages/sources/tags: matching grant; frozen configurations only. Tag relational filters additionally require leads+contacts+tags read and current parents. Do not infer a permission from a successful empty SQL result.
- Lists: existing frozen Page schemas and supported LeadFilter subsets only; unsupported filters422 rather than widening output. Bind signed cursor to staff actor/session/principal version, selected tenant/grant/version/expiry, permission snapshot, resource/filter/sort and capability source revision. Contact tag filters keep ALL-tag semantics and source visibility.
- Every operation explicitly predicates the derived verified tenant, filters archive states and validates the frozen response. Audit only action/resource references and trace; no query text, reason, destinations, result bodies or complete provider data.

## Bounded acceptance before registration

Use real control/issuer/runtime/worker logins in uniquely owned disposable databases after the shared gap fix. Keep tests/control ownership with backend unless reassigned; root owns router/BFF integration tests. Do not run during global role ancestry probes.

1. Missing/forged/expired staff session, wrong issuer/runtime credential and no selected grant cannot read customer rows. Merely setting known tenant/actor/grant GUCs cannot authorize a different opaque-session recipient.
2. Grant body closed-schema/business validation rejects write/export/notes/consent/billing codes, duplicate/empty permissions, blank reason, wrong recipient, inactive recipient, past or >hour expiry, legacy/unknown provenance.
3. Concurrent exact creation yields one grant/Job/audit/key; changed request409. A cut-point crash/replay never renews or recreates. Principal/grant-manager revocation denies replay.
4. Recipient selection matches exact tenant/recipient/grant; wrong grant403/404. Version/context tampering and cross-tenant route IDs deny. Clearing an expired/revoked selected grant and logout work.
5. Context switch changes all selected data/cursor evidence; stale replay/cursor cannot restore or leak a prior selection. Missing related read codes deny, including linked tasks/deals and ALL-tag filters.
6. Archive/source changes before reads deny projected records. Disabled/expired CRM and suspended/archived organization deny. Lock wait crossing grant/entitlement expiry denies after waiting. Current source locks block concurrent revoke/status/capability change until reader transaction ends.
7. Direct reader port uses current sources despite forged typed fields; caller-wide rollback removes grant/Job/audit/key together. Pool reuse clears tenant/actor/session/grant context.
8. Actual recipient read FOR SHARE blocks irreversible revocation; after revoke, API and direct reader fail. Same revocation key preserves one result; changed/stale revision fails. Direct SQL resurrection/expiry widening/CRM writes remain denied.
9. A valid scoped grant exposes only frozen permitted CRM shapes; no customer notes/export/consent/billing/provider payload access. Logging/error tests prove safe Problems and collection redaction. Metadata health privileges do not broaden selected CRM scope or requester Job scope.
10. Root registration/BFF preserves separate cookies, rate/Origin/CSRF guards, private headers, visible reason/expiry banner and mobile selection/expiry states. No production/worker support claims until separately verified.
11. **Real-role entitlement lock/write separation:** with an actual `estate_control` login, live selected recipient grant and verified transaction-local context, FOR SHARE on the current CRM entitlement succeeds. An actual `UPDATE row_version=row_version+1` fails, leaves version/state/expiry unchanged after rollback and cannot be enabled through the baseline permissive tenant policy. Repeat with missing/expired/revoked selection. Verify transaction-bound bootstrap entitlement INSERT and full unselected provisioning still succeed; no actual entitlement UPDATE exception is introduced.
12. **Real-role permissive-policy composition:** keep an owned running provisioning claim current through activation of organization A without completing its Job; select a valid support grant for A in the exact same verified session and set the matching tenant/grant/claim context. Confirm active-organization FOR SHARE succeeds, then prove actual organization status, row_version and updated_at writes fail despite the still-current old claim/check. Probe a selected grant for another organization, an expired/revoked selected grant, and forged support GUCs with the actual session still selected; none may bypass the restrictive selected-context write denial. Finally clear selection and prove the valid unselected initial provisioning activation/Job completion path remains available. Exercise commit/rollback cut points in disposable databases without weakening application guards to obtain the SQL setup.
13. **Opaque-session selection replay:** create two live sessions for the same staff principal. Select A/key1 in session1, then B/key2; replay key1 reloads current B or409 without restoring A/reason. Reusing key1 in session2 cannot read or change session1. Concurrent select/clear commands take own-session FOR UPDATE before ledger replay and serialize without SHARE-upgrade deadlocks; cached Session bodies are never returned as current authority.
14. **Expired/revoked identity-only clear audit:** a recipient with no grant-management permission and no owned control Job clears its own expired/revoked/preserved legacy grant successfully. The approved exact pre-clear audit or immutable control-command audit persists once with the command; rollback leaves both selection and evidence unchanged. Forged previous GUCs, another session's selection or another recipient's grant cannot create a tenant clear audit. An empty/malformed/foreign-recipient selection can still be safely cleared under identity authority with the reviewed non-tenant evidence path. Same-key replay after later selection never silently clears the newer context.

This proposal is ready for shared review. Consumer implementation and database verification remain blocked only on coordinator-approved source-policy/header/selection replay decisions; no production credential is needed for the bounded synthetic slice.
